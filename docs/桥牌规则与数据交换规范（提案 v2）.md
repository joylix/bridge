# 桥牌规则与数据交换规范（提案 v2）

> 状态：提案，待评审　|　日期：2026-10-26 取代：《Bridge Record and Data Exchange Rules — Proposed Revision》（上一版） 依据：仓库 README 与 `docs/`（帮助文档、SRS V0.5、《需求评审与开发建议》、《BRULES v0.4 评审与采用建议》） 范围：叫牌规则交换（BRULES）、牌局与对局记录（PBN / JSON 事件流）、成绩单（CSV）

## 0 阅读指引

## 1 现状摘要

- **运行时**：YAML 规则 + 已冻结的引擎契约（相对座位序列、扁平 AND 条件、优先级 → 具体度 → 声明顺序、ε 探索）。`precision.yml` 有 1074 条规则、36 个在用条件键、54 个优先级值、297 种序列；`natural.yml` 23 条；`leads.yml` 4 条；`signals.yml` 11 条，其中只有 `settings` 的两个阈值真正影响 AI。回归基线为 37 个测试文件 / 447 个用例。
- **规则编辑**：浏览器本地覆盖层（`localStorage`）、「设为当前使用」切换激活文件、`RULES_ADMIN_ONLY` 权限开关。
- **BRULES v0.4**：叫牌规则 DSL（`COND` / `RULE`）加牌例（`DEAL` / `HAND` / `BIDSEQ`）。评审结论：不宜作唯一运行时格式；36 个在用条件键中 10 个可直接映射、4 个部分、22 个无法表达；存在 P0 缺陷。
- **PBN**：当前只实现 Deal；内部另有为 DDS 服务的不等长残局手牌转换。
- **SRS V0.5**：账号体系，`Deal` / `TableBoard` / `SessionBoard` 分层，JSON 事件流，PBN / CSV 导出，导出与回放时点鉴权，留存 365 天、审计 3 年。
- **计分**：得分归赢分方、另一方记 0；IMP 换算；贴点制依赖双方大牌点；流局点数为 `20 − NS 大牌点`。

## 2 设计决策

| # | 决策 |
| --- | --- |
| D1 | **语义权威是规则 IR**（Intermediate Representation，可 JSON 序列化并带 JSON Schema）。YAML 与 BRULES 文本是两种表面语法，都必须无歧义地映射到 IR；两者语义分歧时以 IR 为准。 |
| D2 | **BRULES 的定位**：叫牌规则的可移植交换与外部编辑格式。不承载出牌规则、计分、对局记录或平台数据。 |
| D3 | **运行时不变**：现有引擎契约冻结；BRULES 经编译器进入 IR，再进入现有 `BiddingRule`。采用门槛见 §9。 |
| D4 | **数据分工**：PBN 负责牌局的国际互通；JSON 事件流负责对局记录、回放与审计；CSV 只做衍生报表，不得作为唯一正本。 |
| D5 | **版本与诊断**：所有交换格式声明版本；不支持的版本或特性返回结构化诊断，不得静默丢弃；任何「无损」声明必须有 round-trip 测试支撑。 |
| D6 | **语言**：机器令牌一律英文 ASCII；人读文本（规则说明、昵称等）允许 UTF-8。由此修正 v0.4「仅纯 ASCII」对中文规则说明的限制。 |
| D7 | **存原始事实，派生量重算**：存原始分、大牌点、事件；IMP、贴点点数、队分按口径重算。不得只存一个 IMP 数字。 |
| D8 | **可复现**：每副记录足以重放 AI 决策（种子、规则集内容哈希、各座位配置）。 |
| D9 | **隐私与时点属于格式的一部分**：事件携带可见受众；导出是在释放时点上的投影，而非原始事件流的直接拷贝。 |
| D10 | **分级采用**：当前单机 MVP 只需 Profile S；联网平台的 Profile P 在 SRS 里程碑到达时启用，不阻塞当前阶段。 |

## 3 记号与词法

### 3.1 令牌与大小写

| 类别 | 规则 |
| --- | --- |
| 牌点、花色、座位、叫品令牌 | 大小写不敏感，内部统一规范化为大写 |
| 标识符（规则 id、条件键、JSON 属性名） | 保存原样、区分大小写；规则 id 查重时按大小写不敏感处理 |
| 自由文本（description、昵称） | 保留原始 Unicode 文本 |

同一字符不得因大小写表示两种含义。v0.4 的小写 `x`（小牌通配）与 `X`（加倍）冲突，v0.5 **退役 `x`**：「一张或多张小牌」须用显式牌点集合加长度谓词表达。v0.4 文件由版本专用解析器读取，迁移时 `x` 按 v0.4 原文定义展开，并产生诊断 `LEGACY_WILDCARD_MIGRATED`；无法展开的给 `UNSUPPORTED_FEATURE`。【待核对 v0.4 原文对 `x` 的精确定义】

### 3.2 牌点与花色

牌点为 `A K Q J T 9 8 7 6 5 4 3 2`；`T` 是十的唯一符号，紧凑手牌串与牌点集合中不得出现 `10`（界面可显示 `10`）。花色为 `C D H S`，将牌表示为 `NT`。具体手牌只含真实牌点，不得含通配符；缺门在 PBN 中写 `-`。

### 3.3 叫品令牌

| 含义 | IR | BRULES 文本 | YAML（现有） | PBN |
| --- | --- | --- | --- | --- |
| Pass | `PASS` | `-` | `Pass` | `Pass` |
| 加倍 | `X` | `X` | `X` | `X` |
| 再加倍 | `XX` | `XX` | `XX` | `XX` |
| 实质叫品 | `1C` … `7NT` | 同左 | 同左 | 同左 |

导入器接受别名（`-`、任意大小写的 `Pass`）；导出器按目标格式输出规范记号。单字母 `P` **不是** Pass 的别名，因为它在序列中表示同伴。`X` / `XX` 只在叫品位置有效，在牌点位置无效，解析器必须拒绝，不得重新解释为牌点。

### 3.4 绝对座位与相对座位

绝对座位为 `N E S W`。相对座位在 IR 中为 `ME PAR LHO RHO`，在 YAML 中为 `M P L R`，两者一一对应。定义如下：

- `LHO`：ME 之后紧接着行动的对手（左手敌方）。
- `RHO`：紧邻 ME 之前行动的对手（右手敌方）。
- 顺时针顺序：`ME → LHO → PAR → RHO → ME`。

这与现有引擎 `relSeat` 一致，**与 BRULES v0.4 §1.1 的定义相反**（v0.4 的 P0 缺陷）。

**测试向量 T-SEAT-1**：ME = S，叫牌顺序 N、E、S、W，则 PAR = N，RHO = E，LHO = W。同伴 N 开叫 1NT 后，下一个行动的是 E（RHO），不是 W。v0.4 示例 `PAR:(1NT) + LHO:(-)` 应改为 `RHO`。

`S` 作座位还是花色，由语法位置决定；在 JSON 中座位与花色分属不同字段，不存在歧义。

### 3.5 叫牌结束

- 出现过至少一个实质叫品之后，连续三个 Pass 结束叫牌；中间的 `X` / `XX` 不改变这一规则。
- 四家全 Pass（尚无实质叫品）为流局。
- 速记 `AP` 表示「以必要的剩余 Pass 完成叫牌」，**不是**「追加四个 Pass」。导出 PBN 时，叫牌已结束后不得再追加 Pass。
- v0.4 示例 `…,W:-,allpass` 展开后出现连续 5 个 Pass，属于错误示例，须在 v0.5 中更正。
- 判定以 `core/auction.ts` 为行为基线，测试向量见 §8。

## 4 叫牌规则语义（规则 IR）

### 4.1 文件头与规则对象

文件头字段：

| 字段 | 说明 |
| --- | --- |
| `format` | 固定为 `bridge-rules` |
| `formatVersion` | 如 `0.5`，文法必须允许多位数字 |
| `kind` | `bidding`（v0.5 仅此一种；`lead`、`signal` 另立） |
| `system` / `systemVersion` | 如 `precision`、`natural` |
| `locale`、`author`、`source` | 可选元数据 |
| `defaults` | 可含默认 `priority` |
| `styleParams` | 声明规则所需的风格变量名 |

规则对象字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 满足 `^[A-Za-z][A-Za-z0-9_.-]{0,63}$` |
| `sequence` | 是 | 见 §4.2 |
| `when` | 是 | 见 §4.3，可为空表示无手牌条件 |
| `action` | 是 | 叫品令牌 |
| `priority` | 是 | 整数；缺省值只能来自 `defaults.priority` |
| `description` | 应 | UTF-8，用于叫牌含义浮层与规则编辑器 |
| `tags` | 可 | 如 `natural`、`forcing` |
| `enabled` | 可 | 默认 `true` |
| `examples` | 可 | 随规则携带的测试夹具 |

同一文件内 `id` 不得重复（大小写不敏感），跨文件以 `system + id` 为命名空间；重复为错误，引用无法解析为错误。现有 YAML 已有 `id / description / sequence / when / action / priority`；`tags`、`enabled`、文件头字段为新增，缺省时不影响现有文件。

### 4.2 序列模式 `sequence`

序列是以空白分隔的 `REL:CALL` 元素，按时间从早到晚排列，从叫牌历史**末尾**对齐匹配（后缀匹配）。特殊值：`^$` 表示本副尚无实质叫品，`.*` 表示任意历史（兜底）。例：`P:1C R:Pass` 表示同伴刚叫 1C，随后 RHO Pass，现在轮到 ME。以 `M:` 开头时要求该叫品是 ME 在本副的第一次实质叫牌。【以 `matcher.ts` 为准】

**行为基线**：`engine/matcher.ts` 与 `matcher.test.ts` 是 v0.5 的行为基线。本节文字只是描述，二者不一致时先修订文字或提出变更，不得悄悄改动引擎。

### 4.3 条件 `when`

条件是扁平的「键 → 值」合取（AND）。值的类型有：区间、字符串（如 `stoppers: "SHD"`、`solidSuit: "CD"`）、布尔、风格变量引用 `${name}`。

区间语法：`N`、`N-M`（含端点，N ≤ M）、`N+`，均为整数；无法解析为错误 `INVALID_RANGE`。**具体度**等于 `when` 中的条件项数量。

每个条件键必须在附录 A 中给出：输入、定义、边界、未知时的取值、测试向量。条件分三类：

1. **手牌特征**：如 `hcp`、`controls`、各花色长度、`balanced`。
2. **叫牌进程**：由 matcher 从历史推断，不是手牌特征。
3. **推断量**：`partnerHcp`、`combinedHcp`，取保守下限，仅当同伴是本副第一个实质叫牌人时生效，无法确定时**条件不成立**。

**`balanced` 的语义差异（须显式处理）**：现有引擎的 `balanced` 接受 4333、4432、5332，包括有 5 张高花的 5332；BRULES v0.4 的 `BAL` 排除有 5 张高花的 5332（归入 `UNBAL`）。`precision.yml` 有 219 条规则使用 `balanced`，不得混淆。IR 因此提供 `shapeClass` 枚举：`BAL_ANY`（等同引擎 `balanced`）与 `BAL_NO_5M`（等同 v0.4 `BAL`）。编译器必须把 v0.4 `BAL` 编译为 `BAL_NO_5M`，**不得**编译为 `balanced`；引擎不支持时按 §4.8 展开为多条规则，或返回 `UNSUPPORTED_CONDITION`。`SEMIBAL`、`UNBAL` 的定义【待核对 v0.4 原文】。

### 4.4 叫牌进程、历史与规则 id 耦合

现有引擎已支持、而 v0.4 无法表达的历史语义，v0.5 必须在 IR 中给出对应谓词：

| 需求 | 现有引擎 | BRULES v0.4 | v0.5 要求 |
| --- | --- | --- | --- |
| 本副尚无实质叫品 | `^$` | 无 | 必须 |
| 我是第一个叫牌人 | `M:` 起始 | 无 | 必须 |
| 同伴是开叫人（而非争叫人） | `partnerOpened`（484 条规则使用） | 无 | 必须 |
| 最近一次实质叫品（不论由谁叫） | `lastBidSuit` / `lastBidLevel` | 只能按座位取最近一次 | 必须 |
| 自然套 / 扣叫 / 强自然新花 | `partnerCueBid`、`partnerNaturalSuit` 等 | 无 | 必须 |
| 开叫座位（1–4，自发牌人起） | `openingSeat` | `DEALER` 仅在 `DEAL` 头 | 必须可用于条件 |
| 曾叫过某叫品 | 无 | `EVER:` 仅预留 | 保留；两端都实现前，不得宣称支持 |

**消除对规则 id 命名的隐性依赖**：`partnerForcingNewSuit` / `myForcingNewSuit` 现在靠规则 id 以 `nat_` 开头来判定。规范要求改为显式属性：规则 `tags` 含 `natural`、`forcing`。迁移期由加载器把 `nat_` 前缀映射为 `tags: [natural]`，并产生警告 `LEGACY_ID_PREFIX_SEMANTICS`。

### 4.5 风格变量

`${name}` 在加载时按座位的风格档（0 保守 / 1 正常 / 2 激进，即 `STYLE_PARAMS`）替换；替换后重新做区间校验。变量未声明或无法解析为错误 `UNRESOLVED_STYLE_VAR`。文件头 `styleParams` 列出所需变量，导入方据此判断自己能否提供。

### 4.6 动作与兜底

`action` 为 §3.3 的叫品令牌。动作在当前叫牌状态下非法时，该候选在裁决前被过滤，不属于错误。YAML 中使用了程序不识别的新取值时，导入器必须给出诊断，而不是静默生成无效规则。没有任何候选时，兜底为 `PASS`。

### 4.7 裁决算法（规范性）

候选规则按以下顺序处理，与现有引擎一致：

1. 序列匹配（§4.2）；
2. 条件求值（含风格变量替换）；
3. 动作合法性过滤；
4. 按 `priority` 降序；
5. `priority` 相同时按具体度降序；
6. 仍相同时按声明顺序（稳定排序）；
7. 无候选时兜底 `PASS`。

严格模式（strict）下，同 `priority`、同具体度、但 `action` 不同的候选对必须报 `AMBIGUOUS_RULES`；非严格模式可沿用声明顺序，但必须在文档中说明这是最后的平局规则。

**随机探索**：`randomness = 0` 时严格取排序首位；`randomness > 0` 时以低概率从「次优但有依据」的候选中偏离，**绝不产生非法动作**；随机源为 `mulberry32`，由 `rngSeed` 播种，可复现。所有互通比对与一致性测试必须在 `randomness = 0` 下进行，种子与 `randomness` 必须随记录保存（§6.4）。

**缺省值**：实现不得自行假定缺失 `priority` 的含义；缺省值只能来自文件头 `defaults.priority`，二者皆无则为错误。

### 4.8 量词、花色集合与展开

`U` 表示高花 `{S, H}`，`L` 表示低花 `{C, D}`，仅用于条件，不得作为叫品花色。必须区分存在量词 `ANY(集合, 谓词)` 与全称量词 `ALL(集合, 谓词)`，且量词必须绑定谓词。v0.4 的 `ALL(U)` 没有谓词，语义不可判定，予以退役。示意：两门高花都至少 5 张写作 `ALL(U, LEN>=5)`（示意语法，规范文法以 BRULES v0.5 EBNF 为准；同一语义只允许一种规范写法，不得接受含义不同的歧义变体）。

向现有引擎编译时：

| 构造 | 编译方式 | 诊断 |
| --- | --- | --- |
| `ALL(集合, 谓词)`，集合固定且很小 | 展开为扁平合取，如 `spades: 5+`、`hearts: 5+` | 无 |
| `ANY(集合, 谓词)` 及其他析取 | 展开为多条规则，id 加后缀 `#1`、`#2`，沿用原 `priority` 与声明位置 | `EXPANDED_DISJUNCTION`（info） |
| 嵌套任意布尔（all / any / none） | 暂不支持 | `UNSUPPORTED_FEATURE` |

展开后各分支的具体度各自计算。编译器必须用固定牌例验证展开前后的决策等价，不等价则该规则标记为不可编译。

### 4.9 诊断与导入导出义务

统一诊断对象：`code`、`severity`（`error` / `warning` / `info`）、`message`、`location`（文件、行、列）、`ruleId`（如适用）。稳定的诊断码至少包括：`UNSUPPORTED_VERSION`、`UNSUPPORTED_FEATURE`、`UNSUPPORTED_CONDITION`、`DUPLICATE_ID`、`UNRESOLVED_REFERENCE`、`INVALID_RANGE`、`UNRESOLVED_STYLE_VAR`、`AMBIGUOUS_RULES`、`EXPANDED_DISJUNCTION`、`LEGACY_WILDCARD_MIGRATED`、`LEGACY_ID_PREFIX_SEMANTICS`。

BRULES 导入器必须：解析声明的版本；校验语法与语义；校验引用与 id 唯一；报告不支持的谓词；保留已支持的元数据；输出结构化诊断。导出器必须声明输出是「完整」还是「子集」，不得静默省略规则。

**版本规则**：拒绝未知主版本；1.0 之前按「次版本严格匹配」处理，`0.4` 与 `0.5` 互不兼容，必须使用版本专用解析器，不得把旧文件当作新版本解释。版本号文法必须允许多位数字（如 `0.10`）。

### 4.10 范围外：首攻与跟牌/垫牌规则

`leads.yml`（`id / description / contract_type / role / when / lead / priority`）与 `signals.yml`（`id / description / phase / when / action / priority` 加 `settings`）不属于 BRULES v0.5 范围。IR 为它们预留 `kind: lead | signal`，但 v0.5 不定义交换语义；出牌层另立 `BRULES-PLAY` 子规范。

特别注意：`signals.yml` 的规则列表仅供查阅与后续扩展，真正改变 `playAI` 行为的只有 `settings` 中的两个阈值。任何导出必须用 `executable` 标记区分二者（`settings` 为 `true`，规则列表为 `false`），避免让接收方误以为这些规则都被执行。

### 4.11 规则集身份与覆盖层

运行时实际生效的规则集 = 内置文件 + 覆盖层（单机为浏览器 `localStorage` 覆盖，联网为服务端覆盖）合并后的结果。因此仅记录规则文件名不足以复现 AI 决策。

- **规则集标识**：`rulesetId = SHA-256(规范化 IR)`。规范化序列化：UTF-8、LF、对象键按字典序、规则保持声明顺序、风格变量保持未展开形式。
- 记录必须保存 `system`、`rulesetId`、`overlay`（是否含覆盖层）。
- 联网（Profile P）时规则覆盖只能由服务端管理员修改，对局进行中锁定，不得沿用单机「所有用户可改」的开关。

## 5 PBN 互通

### 5.1 牌局与手牌

- **Deal 串**：`[Deal "N:AKQ.JT9.876.5432 …"]`。冒号前的座位是第一手牌所属座位，其后四手牌按顺时针排列，手牌之间用空格，花色之间用点号，花色顺序为黑桃、红心、方块、梅花；缺门写 `-`；十写 `T`。v0.4 文字写「花色间用空格」而示例用点号，v0.5 以点号为准。
- **初始发牌**必须恰有四手牌、每手 13 张、52 张互不重复；重复牌、缺牌、非法牌点与非法花色必须拒绝。
- **打牌中途快照**（`toPbnHands()` 产生的不等长手牌）只用于内部与 DDS 逐张求解，不是标准 PBN 记录，不得作为 `.pbn` 对外导出；若确需导出，必须在损失报告中声明「非标准残局」。导出对局时 `[Deal]` 始终使用开局快照，打牌过程放入 `[Play]`。这一区分取代上一版 §3.8 对所有手牌一刀切的 13 张要求。
- **局况**：`[Dealer]` 取 `N/E/S/W`；`[Vulnerable]` 写 `None / NS / EW / All`，而 JSON 使用 `NONE / NS / EW / ALL`，二者之间是词表转换，不是字符串直接拷贝。局况未知时省略该标签，不得写成表示真实局况的值。
- **发牌人与前缀**：PBN 语义中 Deal 前缀只表示第一手牌的座位，不等于发牌人。现有导入实现把前缀当作发牌人，v0.5 修正为：发牌人以 `[Dealer]` 为准；`[Dealer]` 缺失时才退化为使用前缀，并产生警告 `DEALER_INFERRED_FROM_DEAL_PREFIX`。

### 5.2 叫牌、定约、结果与文本编码

| PBN 标签 | JSON 字段 | 说明 |
| --- | --- | --- |
| `Board` | `deal.boardNumber` | 整数 |
| `Event` / `Site` / `Date` | `session.*` | `Date` 为 `yyyy.mm.dd` |
| `West / North / East / South` | `seats[*].nicknameSnapshot` | 见下方编码说明 |
| `Dealer` / `Vulnerable` / `Deal` | `deal.*` | 见 §5.1 |
| `Scoring` | `session.scoringMode` | 如 IMP |
| `Auction` | `tableBoard.auction.calls` | 标签值为发牌人；叫品之间空白分隔 |
| `Contract` | `tableBoard.contract` | 如 `4S`、`4SX`、`4SXX`；流局写 `Pass` |
| `Declarer` | `tableBoard.declarer` | 座位 |
| `Result` | `tableBoard.tricksTaken` | 庄家方所得墩数 |
| `Play` | `tableBoard.play.tricks` | 标签值为首攻座位 |
| `Score` | `tableBoard.score.nsRaw` | 带符号，如 `NS 420` |

- **叫牌结束**：导出时叫牌结束后不得追加 Pass；导入时接受 `AP`，展开为使叫牌结束所需的剩余 Pass，不是追加四个。
- **分阶段实现**：与 SRS 一致，先 `Deal`，再 `Auction`，再 `Contract / Declarer / Result`，最后 `Play` 与球员、赛事标签。
- **版本指令与编码**：导出文件首行写 `% PBN 2.1`；PBN 2.1 文本编码以 ISO 8859-1 为主，中文昵称无法直接表示【待对照 PBN 标准原文复核】。因此默认的 PBN 导出在球员标签中使用导出范围内的伪名（如 `Player-1`），完整昵称快照只放在 JSON 中。若提供 UTF-8 PBN 选项，必须在损失报告中声明，并说明部分第三方工具可能无法读取。
- **子集映射**：BRULES 与 PBN 之间只称「子集映射」。BRULES 的 `DEAL / HAND / BIDSEQ` 不再承担牌局交换职责，仅保留作规则 `examples` 夹具；牌局记录一律使用 PBN 或 JSON。

### 5.3 损失报告与无损声明

任何转换无法保留信息时，转换器必须输出损失报告，逐项列出 `field`、`action`（`omitted` / `transformed` / `approximated`）与 `reason`。没有 round-trip 测试支撑，不得声称「无损」。

## 6 JSON 对局记录与事件流

### 6.1 实体模型（与 SRS 对齐）

SRS 的 `Account → Lobby → Room → Session → Board → Table → Seat` 中，`Board` 无法同时表达「同一副牌、多桌各自叫牌出牌」。本规范按《需求评审与开发建议》P0-1 将其拆为三层，建议 SRS 同步修订：

| 实体 | 含义 |
| --- | --- |
| `Deal` | 牌号、四手牌、发牌人、局况；一盘内唯一 |
| `TableBoard` | 某一桌对某个 `Deal` 的叫牌、出牌、定约、结果与原始得分；每桌一份 |
| `SessionBoard` | 同一 `Deal` 各 `TableBoard` 的跨桌聚合（队分、IMP）；属于派生数据，可重算 |

单桌玩法即「一个 `Deal` 只有一个 `TableBoard`」。当前单机 MVP 的 `DealRecord` 约等于 `Deal` 加一个 `TableBoard`；8/16 副的循环累计点数与总点数差属于 Session 层派生视图。

### 6.2 文档信封、版本与缺失值

所有 JSON 文档必须含 `format`（如 `bridge-record`）、`schemaVersion`、`profile`（`standalone` 或 `platform`）、`recordType`、`recordId`、`createdAt`。

- 编码 UTF-8（无 BOM）；时间戳使用 ISO 8601 并带明确偏移，推荐 UTC `Z`。
- `schemaVersion` 与应用版本不得混用。
- 未知的可选字段在安全时应透传；未知的必需语义必须拒绝，或返回明确的「不支持版本」结果。
- **缺失值约定**：字段不适用时省略；字段适用但值未知时显式写 `null`；二者不得互换。状态一律用枚举 `status` 表达，不靠 `null` 暗示。
- 属性名与枚举值使用稳定的英文令牌；本地化显示文本与机器值分离。
- 座位枚举 `N/E/S/W`；局况枚举 `NONE/NS/EW/ALL`。

### 6.3 TableBoard 字段

| 字段 | 说明 |
| --- | --- |
| `deal` | 引用：`dealId`、`boardNumber`、`dealer`、`vulnerability`、`pbn` |
| `status` | `IN_PROGRESS` / `PLAYED` / `PASSED_OUT` / `CANCELLED` / `ADJUSTED` |
| `auction` | `calls`（规范记号数组）与 `completed` |
| `contract` | `level`、`denomination`、`doubled`（`NONE` / `X` / `XX`）；仅在已成约时出现，`PASSED_OUT`、`CANCELLED`、`IN_PROGRESS` 时省略 |
| `declarer`、`tricksTaken` | 庄家座位与庄家方所得墩数（0–13） |
| `play` | `tricks`：每墩含首攻座位、四张牌、赢家 |
| `score` | `nsRaw`（带符号整数，NS 视角，与 PBN `Score` 一致）与 `source`（`computed` / `director`） |
| `hcp` | `ns`、`ew`，全副合计 40 |
| `derived` | 可选：`imp`、贴点后点数及所用口径；必须可由原始事实重算 |

**计分约定转换**：现有实现把得分记给赢分方、另一方记 0，且加倍与再加倍互斥。交换格式统一采用带符号的 `nsRaw`，换算为 `nsRaw = ns − ew`，内部实现可保留两字段；`contract.doubled` 用单一枚举替代两个布尔。`derived` 中的值不得是唯一副本，因为 IMP 与贴点会随口径切换而重算。流局时 `score.nsRaw = 0`，贴点点数 `20 − NS 大牌点` 由派生计算得出，不写入原始分。

### 6.4 复现信息（`engine` 块）

Profile S 起，每个 `TableBoard` 必须携带 `engine` 块，使 AI 决策可以被检查与重放：

| 字段 | 说明 |
| --- | --- |
| `dealSource` | `seeded`（含 `baseSeed`、`index`，对应 `deriveSeed(baseSeed, index)`）或 `imported-pbn`（无种子） |
| `rngSeed` | 叫牌裁决随机源的种子 |
| `ruleset` | `system`、`systemVersion`、`rulesetId`、`overlay`（§4.11） |
| `playRulesets` | 首攻与跟牌/垫牌规则文件的标识（含 `signals` 的 `settings` 阈值） |
| `seats.N/E/S/W` | `controller`（`human` / `ai` / `auto-ai`）、`bidStyle`（0–2）、`playStyle`（0–2）、`randomness`、`ddsPlay`、`ddsSamples`、`objective`（`contract` / `tricks`） |
| `inference` | `auctionConstraints`、`leadInference` 两个开关（基准里用于消融对比） |

**复现承诺的边界**：叫牌决策在相同 `rulesetId`、`randomness = 0`（或相同 `rngSeed`）下应可重算复现。DDS 深度打牌受 Worker 超时与回退影响，**不承诺**重算一致，回放以事件流里记录的实际出牌为准，而不是重新计算。「推荐 + 浮动层解释」不改变牌局状态，不写入记录；其 50 副试用状态只存在本机浏览器，不属于账号数据。

### 6.5 计分层次与派生量

- **原始事实**：`contract`、`tricksTaken`、`score.nsRaw`、`hcp`。这些是正本。
- **计分口径**：`scoringProfile` 只记标识（如 `standard-duplicate`），不把奖分常数写进记录。现有实现取加倍 +50、再加倍 +100，与设计文档示例的统一 +50 不同，应在口径说明中固定。
- **两种 IMP 不得混用**：单桌「计点」是把本副 NS−EW 原始分差经换算表得到的指标，字段记为 `derived.imp.singleTable`；队式赛 IMP 是同一 `Deal` 两桌结果之差的换算，记在 `SessionBoard.teamImp`。
- **贴点**：`本副点数 = IMP −（胜方联手大牌点 − 20）`；流局为 `20 − NS 大牌点`。它是可开关的派生视图，必须保存 `hcp` 才能在开关切换后重算历史与累计。
- **队式赛结算**：`SessionBoard` 由各 `TableBoard` 的原始分重算。验收算例取自评审附录 B：1 号桌红 NS +650、2 号桌红 EW −620，红队 +30，约 1 IMP；2 号桌改判为蓝方宕一后红队 +750，约 13 IMP。调整分只能落在 `TableBoard` 的原始分上，再重算 `SessionBoard`，不得在 IMP 层直接加减。
- **取消与重发**：取消副记 `status = CANCELLED`、原始分 0、0 IMP 并标 `adjusted`；队式赛重发必须该 `Deal` 的所有桌一起，否则只能取消或调整分。
- **MP / VP**：评审建议 V1 删除，而 SRS V0.5 仍保留 MP。格式预留 `derived.mp` 但 V1 不填充，待 SRS 第 10 节裁决。

### 6.6 事件流

事件信封：

| 字段 | 说明 |
| --- | --- |
| `schemaVersion` | 事件模式版本 |
| `streamId` | 一条流对应一个桌或一盘 |
| `seq` | 流内单调递增整数；重复序号或缺口必须被消费者拒绝或显式处理 |
| `eventId` | 全局唯一 |
| `type` | 小写、点号分层，如 `auction.call` |
| `occurredAt` | Profile P 为服务端权威时间；Profile S 为本机时间 |
| `actor` | `kind`（`player` / `ai` / `system` / `admin`），可含 `seat`、`userRef`、`nicknameSnapshot` |
| `audience` | 可见受众，见下 |
| `payload` | 事件载荷 |
| `corrects` | 可选：被更正事件的 `eventId` |

**事件目录**。Profile S：`deal.created`、`auction.call`、`contract.set`、`play.card`、`trick.completed`、`board.completed`、`score.computed`。Profile P 另加：`session.started`、`seat.assigned`、`timeout.auto-pass`、`autopilot.engaged`、`autopilot.released`、`connection.lost`、`connection.restored`、`director.cancel-board`、`director.adjust-score`、`director.redeal`、`session.completed`。

**追加写入**：已完成导出内的事件只增不改。更正用新事件通过 `corrects` 引用；裁判改分记录为 `director.adjust-score`，载荷含前后值、原因、操作人与时间（SRS 7.2），不得改写历史。

**受众 `audience`**：`ALL`（公开，如叫品、已摊开的明手）、`SEAT:<座位>`（仅该座位，如暗手）、`TABLE`（本桌参赛者）、`OPPONENTS_OF:<座位>`（如叫牌提醒，仅对手）、`SPECTATORS_DELAYED`（旁观与转播，延迟后）、`DIRECTOR`、`POSTGAME`（赛后释放）。`deal.created` 的四手牌按座位分别标注 `SEAT:x`，全部四手牌另在 `POSTGAME` 释放。完整事件库保留所有事件，任何对外视图都是对它的投影，与 SRS 视角矩阵（P0-8）和评审附录 C 检查清单对应。

### 6.7 导出投影、时点与隐私（Profile P）

导出是事件流与快照在某个释放时点上的**投影**。释放规则（SRS 6.7 / 7.4）：

1. 单副牌：该 `Deal` 的所有 `TableBoard` 都完成后，才向玩家开放回放与导出；
2. 整盘：`Session` 结束后开放；
3. 对局进行中，禁止导出未完成的牌；
4. 跨桌的进度、定约、结果不得提供给参赛玩家；旁观与转播经延迟后提供（建议固定 30 秒或延迟一副【待 SRS 第 10 节裁决】）；
5. 管理员可提前查看，但必须填写原因并写审计，查看暗手本身留痕。

鉴权在服务端完成，而不是前端隐藏按钮；玩家只能导出自己参与的对局；管理员导出写审计。含四手牌的导出文件必须标 `postGame: true`，并记录 `exportedBy`（伪名）、`exportedAt` 与 `projection`（`role`、`releasedAt`、`gate`）。文件交付后服务端无法撤回。

**身份与隐私**：

- 导出中的球员标识使用 `userRef`，即导出范围内的伪名（如对 `userId` 与导出盐做 HMAC）；不得包含 `username`、`email`、IP，因为 SRS 规定它们只对本人与管理员可见。经审计授权的管理员导出可包含 `userId`。
- 昵称一律为事件发生时的快照（SRS 2.1.4），改名不改写历史。
- 注销或被匿名化的账号：`userRef` 保留伪名，`nicknameSnapshot` 按 SRS 9.6 替换为匿名占位。
- 留存期（对局 365 天、审计 3 年、聊天 90 天、登录日志 180 天、备份滚动 30 天）是运营策略，不写入格式；用户自行保管的导出文件不受服务端留存控制。聊天不属于对局事件流，不进入普通导出。

### 6.8 分级 Profile

| 能力 | Profile S（单机 MVP） | Profile P（联网平台） |
| --- | --- | --- |
| 实体 | `Deal` + `TableBoard` | 增加 `Session`、`SessionBoard`、`Seat`、账号引用 |
| 事件 | 叫牌、出牌、结算 | 增加托管、超时、重连、裁判、换人 |
| 身份 | 无账号，`actor.kind` 区分 human / ai | `userRef` + 昵称快照 |
| 受众与时点 | 不需要 | 必需 |
| 序号与重连 | `seq` 必需 | `seq` + 快照 + `lastSeq` 续传 |
| 规则覆盖层 | 本地 `overlay` | 服务端，仅管理员 |

Profile S 是 Profile P 的严格子集，S 产出的记录必须能被 P 的消费者读取。当前阶段只需实现 S，不应为 P 的需求阻塞开发。

## 7 CSV 成绩单

CSV 是派生报表，不得作为牌局、叫牌、出牌或审计的唯一正本。

- **编码**：UTF-8 **带 BOM**（SRS 7.4，兼容中文 Excel）；分隔符 `,`；按 RFC 4180 加引号；换行 CRLF。
- **空值与数值**：空值为空字段；布尔写 `true` / `false`；得分一律为 NS 视角的带符号整数。
- **列名**为固定的英文 ASCII 令牌；中文表头由界面层提供，不进入机器列名。版本信息放在随包的 `manifest.json`（`schemaVersion`、`generatedAt`、`projection`、列清单），CSV 自身不放版本行。

| 文件 | 一行代表 | 列 |
| --- | --- | --- |
| `boards.csv` | 一个 `TableBoard` | `sessionId`、`boardNumber`、`tableId`、`dealer`、`vulnerability`、`status`、`contract`、`declarer`、`lead`、`tricksTaken`、`overUnder`（±墩）、`nsScore`、`hcpNS`、`hcpEW`、`imp`、`adjusted` |
| `summary.csv` | 一方（`NS` / `EW` 或 `RED` / `BLUE`）在一个 `Session` 内 | `sessionId`、`side`、`boards`、`rawTotal`、`impTotal`、`adjustedPointsTotal` |

成绩单字段必须与界面展示一致（SRS 7.4.5）。导出受 §6.7 的时点与归属约束，且不含 `username`、`email`。

## 8 一致性测试与验收

每个导入器 / 导出器 / 编译器必须通过下列测试；已有对应基线的，直接复用现有测试资产。

| # | 测试 | 基线或向量 |
| --- | --- | --- |
| 1 | 最小合法输入 | 每种格式至少一个最小夹具 |
| 2 | 语法错误与未知版本 | `UNSUPPORTED_VERSION`；`0.4` 文件不得被当作 `0.5` 解析 |
| 3 | 重复 id、未解析引用、未解析风格变量 | `DUPLICATE_ID`、`UNRESOLVED_REFERENCE`、`UNRESOLVED_STYLE_VAR` |
| 4 | 非法牌与非法叫牌 | 重复牌、缺牌、`10`、牌点位置的 `X` |
| 5 | 叫牌结束 | T-AUC-1：`1NT PASS PASS PASS` 结束；T-AUC-2：四个 `PASS` 为流局；T-AUC-3：`1NT X PASS PASS PASS` 结束；T-AUC-4：导出 PBN 时叫牌结束后不追加 Pass；`AP` 展开不超过所需 Pass |
| 6 | 相对座位方向 | T-SEAT-1（§3.4），并与 `matcher.test.ts` 交叉验证 |
| 7 | 记号与大小写 | `x` 不再是小牌；`X` 仅在叫品位置有效；`T` 为十；`pass`、`Pass`、`-` 归一为同一叫品 |
| 8 | 条件词表黄金用例 | 例如带 5 张高花的 5332：`BAL_ANY` 为真、`BAL_NO_5M` 为假；`adjustedHcp` 按附录 A 公式 |
| 9 | 裁决 | 同 `priority` 不同具体度；两者都相同时取声明顺序；严格模式报 `AMBIGUOUS_RULES`；无候选兜底 `PASS`；`randomness = 0` 可复现 |
| 10 | 展开等价 | `ALL` 与 `ANY` 展开前后在固定牌例上的决策一致 |
| 11 | round-trip | 每个声称无损的字段都有往返测试 |
| 12 | 损失报告 | 每个被省略或被转换的字段都有条目 |
| 13 | 规范化确定性 | 同一 IR 两次序列化字节一致；`rulesetId` 稳定 |
| 14 | 事件流 | 重复 `seq` 被拒绝；缺口被检测；`corrects` 引用有效 |
| 15 | 导出时点 | 未完成的 `Deal` 或 `Session` 的导出请求被服务端拒绝 |
| 16 | 隐私 | 导出内容不含 `username`、`email`、IP；昵称为快照 |

**行为回归基线**：现有 37 个测试文件 / 447 个用例必须保持全绿；`npm run benchmark` 与 `npm run bidding-eval` 用固定种子（如 `2026`）比对编译前后。README 中的参考结果提醒：100 副只适合快速回归，1000 副（`seed = 2026`）时平均 +0.42 IMP/副、绝对偏差 5.17 IMP/副、漏局 287、漏贯 97、超叫 46、流局 3，小样本偏乐观。编译等价性比对应使用 1000 副。

## 10 兼容与弃用

- 文法的破坏性变更必须递增格式版本；旧文件由版本专用解析器读取，不得把旧 `x` 重新解释为新含义。
- **v0.4 → v0.5**：`T` 仍为十；`X` 在叫品位置仍为加倍；小写 `x` 仅由 v0.4 解析器识别，不进入新文法，迁移时换成显式谓词并给出 `LEGACY_WILDCARD_MIGRATED`。
- **LHO / RHO 不能机械互换**：v0.4 对二者的定义与标准相反，而且 v0.4 自带示例用法本身前后不一致（评审 §4.1）。迁移工具必须对每条涉及 LHO / RHO 的规则按叫牌顺序位置重新推断，并产生需人工确认的警告，不得全局替换。
- `ALL(U)`、`allpass` 的旧定义、`BAL` 的旧语义同样必须显式迁移。
- 现有无文件头的 YAML 视为 `legacy-yaml`，继续由现有加载器读取；新增文件头后加载器同时接受两种形式。
- **退役清单**：`x` 通配；无谓词的 `ALL(U)`；`allpass` 等于四个 Pass 的定义；把 `DEAL / HAND / BIDSEQ` 当牌局记录；对 `description` 的纯 ASCII 限制；v0.4 的 LHO / RHO 定义。

## 附录 A 条件词表分类

每个条件键在规范里必须补齐「输入、定义、边界、未知时的取值、测试向量」。下表按类别列出 `precision.yml` 中在用的 36 个键（另列已定义但当前规则未使用的键）。

| 类别 | 条件键 |
| --- | --- |
| 手牌特征（13） | `hcp`（713 条使用）、`adjustedHcp`、`controls`、`spades`、`hearts`、`diamonds`、`clubs`、`balanced`（219）、`fourCardMajor`、`noLongSuit`、`noLongSuitExcept`、`aces`、`stoppers`（110）、`solidSuit` |
| 叫牌进程（16） | `openingSeat`、`partnerOpened`（484）、`lastBidSuit`（29）、`lastBidLevel`（24）、`partnerCueBid`（22）、`myCueBid`、`cueBidSuit`、`cueBidSuitNot`、`cueBidLevel`、`partnerSuit`、`mySuit`、`partnerForcingNewSuit`、`myForcingNewSuit`、`partnerBlackwood`、`myBlackwood`、`agreedSuit` |
| 敌方花色相关（4） | `opponentSuitFirstControl`（15）、`opponentSuitStopper`、`opponentSuitNot`、`cueSuitStopper` |
| 推断量（2） | `combinedHcp`、`combinedAces` |
| 已定义、当前规则未使用 | `kings`、`losers`、`voids`、`singletons`、`doubletons`、`partnerHcp`、`partnerNaturalSuit`、`myNaturalSuit`、`cueBidActive` |

其中与 BRULES v0.4 的对应关系为：10 个可直接映射（`hcp`、`controls`、四个花色长度、`balanced`（语义不等价，见 §4.3）、`fourCardMajor`、`noLongSuit`、`noLongSuitExcept`），4 个只能部分表达（`openingSeat`、`aces`、`lastBidSuit`、`lastBidLevel`），其余 22 个无法表达。

**定义示例**（说明规范要写到什么程度，来自 README，落地前以 `evaluate.ts` 与 `conditions.ts` 为准）：

- `hcp`：A=4、K=3、Q=2、J=1，全副 40 点。`controls`：A=2、K=1。
- `adjustedHcp`：`AP = HCP + 长套点 + 短套点 + 坚固套奖励 − 敌方花色废点`。长套点取最长进攻花色（敌方花色除外，除非它本身是将牌）的第 5、6、7 张各 +1，最多 +3；短套点仅在同伴已显示支持、将牌明确时计入，旁门缺门 +3、单张 +2、双张 +1；坚固套奖励为最长花色 7 张以上且以 A、K、Q 领衔时 +1；敌方花色中只有单张 K、Q、J 时扣 1；调整量限制在 `[-2, +7]`。原始 `hcp` 仍用于计分与贴点。
- `partnerHcp` / `combinedHcp`：保守下限推断，仅当同伴是本副第一个实质叫牌人时生效，无法确定时条件不成立。
- `openingSeat`：1 为发牌人，2、3、4 依次为其后三家，仅用于开叫规则。
