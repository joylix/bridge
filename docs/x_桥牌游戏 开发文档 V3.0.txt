# Node.js 桥牌游戏（网页版+APP双模式）完整开发文档 V3.0

## 一、项目概述

### 1.1 项目定位
本项目是一款基于 Node.js 开发的桥牌游戏，首期优先实现网页版，支持多种对局模式（全机器对战、人机对战、多人混战），可自定义叫牌规则、出牌信号，并为机器人同伴提供独立风格设定（激进/保守/中庸）；内置自动累积实战知识库实现AI自进化；后期扩展为安卓/iOS移动端APP，同时支持联网真人对战（对接自建网络桥牌服务器）与完全离线本地游戏，最终形成“网页版+移动端APP”、“联网+离线”、“机机对战+人机对战+真人对战”的全场景桥牌游戏体系。核心目标：兼顾开发效率与长期扩展性，复用开源资源降低开发成本，前期聚焦网页版落地，提前预留移动端与联网功能扩展接口，确保后期升级无重构、低返工。

### 1.2 核心价值
- **规则灵活**：支持自定义叫牌体系、约定信号、防守信号，初期提供主流规则模板并支持关键参数微调，适配不同用户的规则需求，区别于固定规则的桥牌游戏。
- **AI智能**：通过实战知识库自动累积对局数据，AI可基于历史特征统计、双明手求解器（后期引入）与模型反馈持续优化决策，实现“越玩越智能”。
- **多端兼容**：首期网页版，后期无缝扩展移动端APP，支持联网真人撮合与离线本地游戏，覆盖多场景使用需求。
- **高效落地**：复用成熟开源桥牌规则库与项目架构，降低核心逻辑开发成本，聚焦自定义功能与扩展能力搭建。

## 二、需求分析

### 2.1 首期需求（网页版，核心必做）

#### 2.1.1 基础桥牌功能
- **牌桌可视化**：网页端展示四家机器人（北/南/东/西）站位、手牌、叫牌进程、出牌区域，支持出牌动画。
- **基础对局流程**：实现随机发牌（含局况设定）、叫牌（支持Pass、加倍、再加倍）、**明手（Dummy）摊牌与庄家代理出牌**、**声称/摊牌（Claim）提前结算（首期机机对战自动判定）**、出牌、赢墩判定、定约结算、得分统计（支持标准桥牌计分，考虑局况轮转）。
- **多模式对战**：
  - 全机器对战：南北机器 VS 东西机器，支持连续多局自动运行，无需人工干预。
  - 人机对战：支持1个真人（默认南位，后期可选任意座位）与3个机器人对局。
  - 混编对战：支持多个真人 + 机器人补齐至4人（为后期联网对战打基础）。
- **机器人同伴风格设定**：可为机器人选择**叫牌风格**与**出牌风格**，统一为三档 **0 保守 / 1 正常 / 2 激进**；另可设置 **随机度 randomness（0~1）**控制“不可预测性”（0 = 严格按规则，越大越可能在合法候选中偏离到次优但有依据的选择，增加趣味性且保证可复现）。风格与随机度均**独立于规则配置**，可针对不同座位单独设置（术语上以 0/1/2 三档替代“激进/保守/中庸”的模糊表述）。

#### 2.1.2 自定义规则功能
- **叫牌规则自定义**：首期提供主流叫牌模板（如自然叫、精确叫），支持在模板基础上调整关键参数（如1NT点力区间、弱二阻击条件等）。系统内置规则冲突检测器，保存配置时自动校验并提示潜在冲突。后期逐步开放更细粒度的自定义（嵌套布尔条件、候选打分模型）。
- **规则引擎契约（冻结）**：叫牌与出牌是**两套独立 Schema**，共享同一匹配内核与封闭条件词表；叫牌序列以**相对座位 token**表达（`M/P/L/R`），可识别敌方干扰；候选经“优先级/具体度/声明顺序”确定性裁决，且必须通过动作合法性过滤。具体规范见 MVP 设计文档第 4 章（冻结后各阶段沿用）。
- **出牌信号自定义**：支持配置首攻约定（如长三、长五）、跟牌/垫牌基本规则。完整的防守信号体系（长短信号、姿态信号等）定为后期迭代内容。
- **规则可视化配置**：网页端提供配置面板，支持修改规则参数、保存配置方案，无需修改代码即可切换规则体系。

#### 2.1.3 实战知识库功能
- **自动累积**：每局对局结束后，自动结构化存储对局数据（手牌分布、局况、叫牌序列、出牌进程、定约成败、得分，后期含理论最优分Par Score）。
- **AI适配与自进化**：AI决策时，提取当前手牌与叫牌序列的特征（大牌点分桶、牌型分布编码、叫品抽象），利用特征哈希快速检索相似历史案例，统计各候选叫品/出牌的胜率。同时，定期对累积数据进行离线分析，更新轻量级决策权重表，供AI在线调用，实现从“被动查表”到“主动优化”的闭环进化。**AI查询知识库严格遵循视角隔离：防守方AI无法直接读取对方阵营的策略配置，只能基于可观察的出牌进行推断。**
- **数据查看**：网页端支持检索对局记录、查看知识库牌例，可复盘对局过程。

#### 2.1.4 基础辅助功能
- **对局回放**：支持单局步进回放、倒放，查看每一步叫牌、出牌细节。
- **日志记录**：记录对局日志、AI决策日志，便于调试与问题定位。
- **响应式布局**：网页端适配电脑、平板屏幕，为后期移动端WebView套壳预留适配基础。

### 2.2 后期需求（APP端+联网功能，预留扩展）

#### 2.2.1 移动端APP需求
- **双端适配**：开发安卓/iOS APP，一套前端代码（优先Flutter）编译双端，体验接近原生。
- **双模式支持**：
  - 联网模式：连接自建Node.js桥牌服务器，实现真人实时撮合、房间对战、积分排位。
  - 离线模式：不联网状态下，纯本机运行AI对战（含人机/全机器）、自定义规则、本地知识库累积，无网络依赖。
- **本地存储**：APP内置轻量数据库，存储本地规则配置、离线对局记录、本地知识库。
- **多端同步**：支持离线对局记录、自定义规则、知识库数据，联网后同步至云端。

#### 2.2.2 网络桥牌服务器需求
- **用户体系**：支持注册/登录（手机号、微信）、游客模式，存储用户头像、积分、段位、历史战绩。
- **匹配撮合**：支持快速匹配（4人随机一桌）、自建私密房间（邀请好友）、俱乐部房间、比赛专用桌。
- **实时同步**：通过WebSocket实现多端（网页、APP）对局状态同步，**强制实施视角隔离，只推送当前玩家应见信息**，确保叫牌、出牌无延迟、无错乱。协议支持全量/增量推送，并引入序列号机制防止指令乱序；支持断线重连时的状态精确恢复。
- **比赛体系**：支持双人队式赛、淘汰赛、循环赛，自动编排赛程、积分排名，统一叫牌规则模板。
- **权限管理**：实现座位锁定、操作权限控制（同一时间仅一人可操作）、旁观模式。

#### 2.2.3 扩展需求
- **AI教练**：对局结束后，AI自动点评叫牌瑕疵、防守失误，提供最优打法建议。**评价标准基于实际得分与理论最优分（Par Score）的差距。**
- **多套规则切换**：支持一键切换自然叫、精确叫、自制规则体系，保存多套配置方案。
- **批量对局**：支持后台批量运行对局，生成规则优劣对比报表，优化AI决策参数。
- **真人对战中的Alert机制**：非自然叫品需向对手警示并解释，前期在协议和数据模型中预留字段。

### 2.3 非功能性需求
- **性能**：网页端对局无卡顿，AI决策响应时间 ≤ 500ms；单服务器支持上千人在线、几百张牌桌同时运行。
- **兼容性**：网页端兼容Chrome、Edge、Firefox等主流浏览器；APP兼容安卓8.0+、iOS 12.0+。
- **可扩展性**：核心逻辑模块化、低耦合，通过接口隔离实现跨端复用，支持后期新增功能（如真人对战、比赛系统）时无需重构。
- **可维护性**：代码规范、注释完整，配置文件清晰，便于后期修改规则、修复Bug。
- **安全性**：联网模式下防止作弊（后端强制校验规则），**对局状态推送实施视角隔离，禁止将防守方/未摊牌暗手数据泄露给无关客户端**；用户数据加密存储，对局记录不可篡改。

## 三、技术方案

### 3.1 整体架构设计（兼顾首期与后期扩展）
采用“通用内核+多端适配”的分层架构，核心逻辑抽离为独立模块，通过定义抽象接口实现“一份内核、多端部署、联网离线双模式”，确保首期网页版开发与后期APP扩展无缝衔接。

#### 3.1.1 架构分层（从下到上）

1. **通用内核层（核心，纯JS/TS，无网络与IO依赖）**
   - **基础规则模块**：发牌、牌型判定、叫牌规则校验、出牌规则、赢墩计算、计分系统（复用开源库）。
   - **AI决策模块**：基于规则配置+特征化知识库案例匹配的决策逻辑，支持自定义规则解析、机器人风格参数（0 保守 / 1 正常 / 2 激进）与随机度、双明手求解器（DDS）扩展接口。所有AI计算接口设计为异步（返回Promise），为未来用WebAssembly重写核心模块预留空间。
   - **知识库模块**：对局数据结构化处理（含理论最优分）、特征提取与哈希、统计胜率、定期模型更新逻辑。该模块仅依赖存储接口的抽象，不直接进行IO。
   - **规则配置模块**：自定义叫牌/出牌规则解析器、配置Schema校验与冲突检测、多套规则管理、机器人风格配置。
   - **核心特点**：无网络依赖、无IO耦合（通过接口依赖倒置），可同时运行在Node.js服务端、网页端Worker线程、APP本地JS引擎。

2. **服务端适配层（Node.js专属，首期开发，后期扩展）**
   - **通信模块**：WebSocket（Socket.io）实时通信，处理前端/APP的指令与状态推送，**实施视角隔离掩码**，支持断线重连时的状态快照恢复。
   - **对局管理模块**：房间创建、桌位管理、**含明手控制权转移、声称自动判定与投票（后期真人）的对局状态机调度**（发牌→叫牌→打牌→结算）、多局连续运行。
   - **数据存储模块**：实现内核定义的存储接口，包含云端知识库（SQLite/后期PostgreSQL）、用户数据、对局记录存储。
   - **扩展预留**：用户体系、匹配撮合、比赛系统、权限管理的接口预留。

3. **客户端适配层（多端共用，分阶段开发）**
   - **网页端**：Vue3/React + Element Plus，负责牌桌可视化（含明手摊牌、庄家代理出牌交互）、规则配置面板（含机器人风格选择）、对局回放、用户交互。
   - **APP端（后期）**：Flutter，负责双端编译、本地内核加载（通过flutter_js）、本地数据库实现、联网/离线模式切换、原生交互（推送、桌面图标等）。
   - **核心特点**：UI与业务逻辑分离，仅负责视图渲染与指令传递，不包含任何桥牌核心规则。

#### 3.1.2 通信协议设计（标准化，预留扩展）
采用WebSocket（Socket.io）实现实时通信，定义统一事件指令格式，引入序列号、视角掩码与状态同步模式，确保网页端、APP端、服务端通信兼容，后期扩展无需修改协议。

| 事件类型 | 指令格式 | 说明 |
|---------|---------|------|
| 入座 | `{type: "seatEnter", data: {seat: "north/south/east/west", userId: "...", isHuman: true/false, botStyle: {bid: 0|1|2, play: 0|1|2, randomness: 0.0}}, seq: 123}` | 用户/机器人入座，指定座位，真人标识与机器人风格（0保守/1正常/2激进）及随机度 |
| 叫牌 | `{type: "bidAction", data: {seat: "...", bid: "1S/2NT/加倍/再加倍/Pass", alert: false, alertDesc: ""}, seq: 124}` | 发送叫牌指令，alert字段为后期延用 |
| 出牌 | `{type: "playCard", data: {seat: "...", card: "S10/H5", controlSeat: "north"（可选，庄家代理明手时此字段指明操作者）}, seq: 125}` | 发送出牌指令，后端校验合法性 |
| 声称 | `{type: "claim", data: {seat: "...", claimTricks: 3, type: "claim/concede"}, seq: 126}` | 玩家提出声称或认输 |
| 对局状态推送 | `{type: "gameState", data: {state: "发牌/叫牌/打牌/结算", currentSeat: "...", controlSeat: "...", cards: {...（经视角掩码）}, bids: [...], mode: "FULL/DELTA"}}` | 后端向客户端推送实时对局状态，全量用于重连，增量用于常规更新，cards字段仅包含当前玩家有权看到的暗手信息 |
| 规则配置 | `{type: "ruleConfig", data: {callRules: {...}, playRules: {...}, botStyles: {north: {...}, south: {...}, east: {...}, west: {...}}}, seq: 127}` | 客户端提交自定义规则及机器人风格，后端校验并保存 |

### 3.2 技术选型（兼顾成熟度与扩展性）

#### 3.2.1 后端技术栈（Node.js）
- **核心框架**：Express/Koa（轻量、易扩展，适合搭建API与WebSocket服务）。
- **实时通信**：Socket.io（支持长连接、断线重连，适配多端通信）。
- **开源规则库复用**：
  - `contract-bridge`（npm包）：复用发牌、牌型、定约等基础逻辑，评估后进行充分单元测试及必要改造。
  - `bridge-scorer`（npm包）：辅助实现标准/自定义计分逻辑。
- **可选AI增强**：后期集成双明手求解器（DDS）的WebAssembly编译版或Node.js原生绑定，作为AI出牌决策和AI教练的算力底座。
- **数据存储**：
  - 首期：SQLite（轻量、无需部署，适合本地知识库与对局记录存储）。
  - 后期：PostgreSQL（支持大规模数据、复杂查询，适配用户体系与全局知识库）。
- **工具类**：lodash（牌型组合运算）、mathjs（牌力估值）、winston（日志记录）、Jest（单元测试）。

#### 3.2.2 网页端技术栈
- **框架**：Vue3（易上手、组件化，适合快速搭建可视化界面）。
- **UI组件库**：Element Plus（快速实现配置面板、牌桌布局、弹窗等组件）。
- **可视化**：原生CSS+DOM（牌桌、卡牌展示），GSAP（可选，实现出牌动画）。
- **通信**：Socket.io-client（与后端WebSocket通信）。

#### 3.2.3 移动端APP技术栈（后期）
- **核心框架**：Flutter（一套代码编译安卓/iOS，原生体验好，支持内嵌JS内核）。
- **JS内核调用**：flutter_js（在Flutter中嵌入运行纯JS通用内核）。
- **本地存储**：sqflite（Flutter专属轻量数据库，适配离线知识库与对局记录）。
- **通信**：web_socket_channel（与后端WebSocket通信，复用网页端协议）。

#### 3.2.4 开源项目参考与复用策略
**核心原则**：复用成熟开源资源的基础功能，自研核心特色功能（自定义规则、知识库、多端适配），避免重复造轮子，同时确保架构可控、无耦合。

| 开源项目/库 | 复用内容 | 改造/自研内容 |
|------------|---------|-------------|
| contract-bridge | 牌张模型、发牌、牌型分布、定约判定、计分基础 | 扩展支持固定牌局复盘、局况轮转；改造计分对接自定义规则；暴露校验接口 |
| devennorton/bridge | Node.js+Socket.io通信架构、UI布局参考、状态管理 | 删除固定叫牌/出牌规则，替换为自研通用内核与可配置AI；改造对局管理支持连续运行、明手控制权转移、声称机制与规则切换；增强前端增加配置面板与知识库检索 |
| bridge-scorer | 标准计分逻辑 | 定制化调整以适配自定义叫牌体系下的分数计算 |
| DDS（Double Dummy Solver，后期） | 双明手精确计算赢墩与最优打法 | 编译为WebAssembly或Node.js绑定，封装为异步服务，供AI出牌决策、AI教练使用 |
| flutter_js / sqflite | Flutter中运行JS、本地数据库 | 封装为符合内核存储接口的适配器，实现离线模式下的本地存储与内核调用 |

### 3.3 核心模块详细设计

#### 3.3.1 通用内核模块（核心复用模块）

1. **牌张与发牌模块**
   - 复用contract-bridge的牌张模型（52张牌，花色、点数定义）。
   - 扩展发牌功能：支持随机发牌（含局况随机设定）、固定牌局复盘、牌型分布统计。
   - 输出接口：`dealCards()`（发牌，返回含局况数据）、`getCardType()`（牌型判定）。

2. **规则引擎模块**
   - 配置解析：读取叫牌/出牌规则（MVP 采用 YAML，后续可切换/并存 JSON），校验规则合法性并执行冲突检测，提前标记潜在冲突。
   - **引擎契约（冻结，MVP 已落地）**：
     - 决策上下文按类型冻结、**不得混用**：叫牌上下文 = 手牌 + 叫牌史（含**座位归属**）+ 当前最高叫品 + 自身风格；首攻上下文 = 手牌 + 定约类型 + 明手牌。
     - 规则 = `条件组合（扁平 AND）→ 动作/策略` + `priority`；条件词表**封闭且可扩展**（hcp、controls、花色长度、均型…），支持风格变量引用。
     - 叫牌序列采用**相对座位 token**（`M/P/L/R` 相对当前叫牌人）从末尾匹配，从根上支持敌方干扰识别。
     - 裁决顺序：**优先级↓ → 条件具体度↓ → 声明顺序**，保证确定性；候选必须通过**动作合法性过滤**（不产出低于当前叫品的叫品）。
     - 规则匹配**无状态**：纯函数，不保留对局记忆。
   - 出牌规则校验：内核校验出牌合法性（跟牌、将吃、垫牌规则）；打牌决策以算法为主，规则引擎只负责首攻/信号等“浅层”约定。
   - 输出接口：`parseCallRules()`、`validateBid()`、`validatePlay()`、`detectRuleConflicts()`（规则冲突检测）。
   - **分期红线**：MVP/阶段二只做“模板化 + 扁平条件 + 冲突检测”，**嵌套布尔（all/any/none）与候选打分模型推到后期**，避免引擎过度设计。

3. **AI决策模块**
   - **风格注入**：每个AI实体持有 `bidStyle` 与 `playStyle`（**0 保守 / 1 正常 / 2 激进**），以及独立的 `randomness`（探索度，[0,1]）。风格以**阈值参数覆盖**实现（如 1NT 点力区间、争叫点力下限、阻击长度要求），**不复制规则文件**，保证风格与规则正交、可自由组合。
   - **基础决策**：基于自定义规则及风格，产出全部合法候选 → 按“优先级/具体度/声明顺序”裁决 → 选择合法叫品/出牌。
   - **探索（趣味性/随机性）**：以 ε-greedy 方式，按 `randomness` 概率在**仍合法且有依据的次优候选**间选择；`randomness=0` 时严格取最优。**硬约束**：探索范围永远限定于合法候选，绝不产生非法或“明显错误档位”的动作；随机源由 `seed` 播种，保证可复现。
   - **智能决策与进化**：
     - 实时决策（阶段二起）：将当前手牌及叫牌进程转换为多级特征键（大牌点分桶、牌型分布编码、叫牌序列抽象），查询知识库模块的`getWinRate(featureKey, candidateAction)`接口，优先选择统计胜率最高的合法候选。
     - 离线进化：知识库模块提供`updateWeights()`方法，定期根据新增对局数据重新计算特征权重表，AI决策直接加载最新的权重表，实现持续优化。
     - **与探索的协同**：探索产生的对局同样是学习样本，故探索必须“有依据地偏离”而非纯噪声，避免污染胜率统计。
   - **高级决策（阶段三及以后）**：预留`ddsAnalyze()`异步接口，后续集成DDS，在出牌阶段调用双明手分析结果，实现精准打牌。
   - **安全隔离**：AI策略在查询知识库或进行态势评估时，必须传入当前玩家`perspective`参数，确保无法访问未授权信息（如对方实际手牌、对方未公开的防守信号配置）。
   - 输出接口：`getAIBid(hand, seq, style, perspective)`、`getAIPlay(hand, seq, style, perspective)`。

4. **知识库模块**
   - 数据结构：每局对局结构化存储，包含手牌分布、局况、叫牌序列、出牌进程、结果、理论最优分（`par_score`，后期启用）。
   - 存储适配：定义抽象存储接口`IKnowledgeRepository`，包含`saveGame()`, `queryByFeature()`, `queryAllForAnalysis()`等方法。服务端适配层和APP适配层分别实现该接口。
   - 案例匹配与降维策略：
     - **特征提取**：从牌局中抽取可归类的关键特征，而非完整牌面。例如：
       - 大牌点（HCP）分桶：0-5, 6-9, 10-12, 13-15, 16-18, 19+
       - 牌型分布编码：如5-3-3-2、4-4-4-1等
       - 失张数（LTC）
       - 叫牌序列抽象：开叫类型（Pass/1阶高花/1阶低花/1NT/2阶阻击），应叫类型，竞叫是否发生
     - **多级哈希**：将以上特征组合为复合键，快速命中对应桶。桶内以胜率排序。
   - 输出接口：`saveGameData(gameRecord)`、`getWinRate(featureKey, action)`、`updateWeights()`、`queryByParScore()`（后期）。

#### 3.3.2 服务端模块（首期开发）

1. **WebSocket通信模块**
   - 建立长连接：处理客户端（网页）连接、断线重连、心跳检测。
   - 指令处理：接收客户端叫牌、出牌、规则配置、声称等指令，调用内核模块校验并执行；利用序列号保证指令有序处理。
   - **断线重连机制**：服务端缓存每个活跃对局的完整事件日志。客户端重连时发送`{type: "reconnect", data: {lastSeq: 100}}`，服务端根据序列号推送增量事件或全量快照（`FULL`模式），确保客户端状态精确恢复。
   - **视角掩码推送**：调用`gameState`生成函数时，传入当前目标座位，对所有牌手卡牌进行过滤：仅当牌手为明手（已摊牌）或定约方按规则可查看时，才下发具体牌面；其余座位仅下发牌数量。

2. **对局管理模块**
   - 房间创建：支持单局房间、多局连续房间，管理房间生命周期；房间内可配置真人/机器人座位及机器人风格。
   - 桌位管理：锁定四家座位，处理真人/机器人入座、离席、托管逻辑。
   - **对局状态机**：严格定义并调度以下阶段转移：
     - `BIDDING`：叫牌，包含Pass计数、加倍/再加倍逻辑；结束时判断是否产生定约。
     - `DUMMY_SETUP`：首攻后明手摊牌，控制权转移给庄家。
     - `PLAYING`：打牌，庄家同时操作自己与明手的牌；牌手出牌后自动推进墩循环。
     - `CLAIM_PHASE`（首期机机自动判定，后期真人投票）：若AI判断剩余墩数绝对必然（通过规则或未来DDS），自动触发提前结算；真人模式下发起投票，全部同意则结算，有人拒绝则继续打牌。
     - `SETTLEMENT`：结算得分，触发知识库存储与日志。
   - 对局调度：支持多局自动运行，保持状态机上下文。

3. **数据存储模块**
   - 知识库存储：实现内核定义的`IKnowledgeRepository`接口，每局结束后自动保存，初期使用SQLite。
   - 规则配置存储：保存用户自定义的叫牌/出牌规则及机器人风格配置，支持多套配置切换。
   - 日志存储：记录对局日志、AI决策日志，便于调试与复盘。

#### 3.3.3 网页端模块（首期开发）

1. **牌桌可视化模块**
   - 布局：展示四家机器人/真人站位、手牌区域、叫牌面板、出牌区域、计分面板。
   - **明手交互**：当玩家是庄家时，手牌区同时展示明手摊开的牌，且玩家可点击明手牌张进行出牌。
   - **风格选择**：入座或开局前，可为每个机器人座席选择叫牌风格和出牌风格。
   - 交互：支持查看手牌详情、回放对局、修改规则配置。
   - 动画：实现出牌、叫牌的简单动画，提升体验。

2. **规则配置模块**
   - 配置面板：提供下拉框、输入框，选择规则模板（如自然叫、精确叫），并调整关键参数（如1NT点力范围、二三阶阻击条件等）；同时提供机器人风格设置区域（0 保守 / 1 正常 / 2 激进）与随机度滑块。完整自定义功能后期开放。
   - 配置保存：将用户配置转为JSON格式，提交至服务端保存，支持本地缓存。
   - 规则校验：前端进行基本参数范围校验，后端进行规则冲突检测，确保配置有效。

3. **对局回放模块**
   - 记录对局每一步操作序列，支持步进回放、倒放、暂停。
   - 展示每一步叫牌、出牌细节，标注赢墩归属、定约进度。

#### 3.3.4 移动端APP模块（后期扩展）

1. **模式切换模块**
   - 联网/离线切换开关，自动检测网络状态，默认优先联网模式。
   - 模式适配：联网时连接服务端，离线时加载本地内核与本地数据库。

2. **本地运行模块**
   - 通过flutter_js嵌入通用JS内核，本地运行发牌、AI决策、规则校验。
   - 实现`IKnowledgeRepository`接口的sqflite版本，注入内核，使本地知识库累积与AI进化功能离线可用。

3. **多端同步模块**
   - 联网后，自动同步本地对局记录、知识库数据至云端。
   - 同步云端自定义规则、用户积分、段位至本地。

#### 3.3.5 网络桥牌服务器扩展模块（后期）
1. **用户体系模块**：注册/登录、用户信息管理、积分/段位计算与存储。
2. **匹配撮合模块**：快速匹配算法、房间创建与管理、好友邀请功能。
3. **比赛系统模块**：赛程编排、积分排名、比赛规则统一配置。
4. **权限管理模块**：操作权限控制、座位锁定、旁观模式、作弊检测（基于视角隔离与行为分析）。
5. **Alert警示模块**：真人对战中，对非自然叫品触发警示流程，通知对手并展示解释。

### 3.4 数据存储设计

#### 3.4.1 首期存储（网页版+本地知识库）
- **数据库**：SQLite（轻量、无需部署，适合首期快速落地）。
- **核心表结构**：
  - `game_records`（对局记录）：id、game_id、deal_data（手牌分布）、vulnerability（局况）、bid_sequence（叫牌序列）、play_sequence（出牌序列）、contract（定约）、score（得分）、par_score（理论最优分，后期字段）、create_time（创建时间）。
  - `rule_configs`（规则配置）：id、config_name（配置名称）、call_rules（叫牌规则JSON）、play_rules（出牌规则JSON）、bot_styles（机器人风格JSON）、create_time。
  - `knowledge_base`（知识库）：id、feature_key（多级特征哈希键）、action（叫品或出牌）、win_count（成功次数）、total_count（总次数）、win_rate（动态胜率）、last_updated（最后更新时间）。
  - `decision_weights`（决策权重表，用于AI进化）：id、feature_key、action、weight（权重系数）、update_time。

#### 3.4.2 后期存储（APP+联网服务器）
- **云端数据库**：PostgreSQL（支持大规模用户数据、复杂查询）。
- **新增表结构**：
  - `users`（用户表）：id、phone、wechat_id、avatar、nickname、score（积分）、rank（段位）、create_time。
  - `rooms`（房间表）：id、room_id、creator_id、status（房间状态）、rule_config_id、create_time。
  - `room_members`（房间成员表）：id、room_id、user_id、seat（座位）、is_human、bot_style（机器人风格）、status（在线状态）。
  - `matches`（比赛表）：id、match_id、type（比赛类型）、schedule（赛程）、rank_list（排名）、create_time。
- **本地存储（APP）**：sqflite，实现与云端相同的存储接口，表结构与云端一致，仅存储本地离线数据，联网后同步。

## 四、分阶段实施策略

整体分4个阶段实施，首期聚焦网页版落地，后期逐步扩展APP与联网功能，每阶段完成后进行测试验收，确保架构兼容、功能可用，避免后期返工。

> **落地规范说明**：本阶段计划的具体编码规范以《桥牌游戏 MVP 开发文档 V1.4》与《桥牌游戏 MVP 详细设计文档 V1.4》为准——它们已冻结规则引擎契约（决策上下文、条件词表、相对座位序列、裁决与探索算法、风格参数表）与人类控制权模型。后续阶段在**不改变这些契约**的前提下扩展；若确需演进，走“接口版本化 + 兼容层”，避免返工。

### 阶段一：基础骨架搭建（1周，核心：复用开源+搭建架构）
**核心目标**：完成项目基础架构搭建，复用开源库实现基础桥牌功能，打通前后端通信，实现简单机机对战。

**具体任务**：
1. 项目初始化：创建Node.js后端项目（Express/Koa）、Vue3前端项目，配置依赖（Socket.io、contract-bridge等）。
2. 复用开源资源：
   - 集成contract-bridge，实现发牌、牌型判定、基础计分功能，编写单元测试验证其逻辑正确性。
   - 参考devennorton/bridge，搭建WebSocket通信架构，实现前后端实时连接。
3. 核心架构抽离：将桥牌基础规则抽离为通用内核模块（纯JS/TS），并定义抽象存储接口`IKnowledgeRepository`，确保无IO耦合。
4. 基础UI搭建：网页端实现简单牌桌布局、四家机器人站位、手牌展示。
5. 简单机机对战：实现四机器人自动发牌（含局况）、固定规则叫牌/出牌，完成单局对局，验证基本状态机（不含明手控制权、声称等高级特性）。

**验收标准**：
- 前后端WebSocket通信正常，无断线、无延迟。
- 可正常随机发牌（含局况），机器人自动叫牌/出牌，完成单局结算。
- 通用内核模块可独立调用，无网络/IO耦合，满足接口分离要求。

### 阶段二：网页版核心功能开发（2-3周，核心：自定义规则+知识库+人机对战）
**核心目标**：完成网页版核心功能，实现自定义规则配置（模板化+机器人风格）、人机对战、实战知识库自动累积与AI进化闭环、智能决策，并完善桥牌特有流程（明手、声称）。

**具体任务**：
1. 自定义规则与机器人风格：
   - 设计叫牌/出牌规则JSON Schema，实现规则解析、校验及冲突检测功能。
   - 网页端开发规则配置面板，初期提供自然叫、精确叫等模板，支持调整关键参数；增加机器人风格独立设置（0 保守 / 1 正常 / 2 激进）与随机度。
   - 改造AI决策逻辑，使其支持读取自定义规则与风格参数，输出合法叫品/出牌。
2. 人机对战与多人混编：
   - 扩展房间创建，支持选择真人座位（首期默认南位）及机器人补齐。
   - 实现真人与机器人同界面交互，真人通过UI操作，机器人自动决策。
3. 对局流程完善：
   - 在状态机中加入明手（Dummy）摊牌及庄家代理出牌的完整逻辑，前端实现对应交互。
   - 实现机机自动声称判定（基于简单规则或未来DDS），提前结束必然墩。
4. 实战知识库开发：
   - 设计SQLite表结构（含特征键与权重表），实现`IKnowledgeRepository`接口的服务端版本，支持自动入库。
   - 开发多级特征提取与哈希算法，快速匹配相似案例，实现基于统计胜率的AI决策（遵循视角隔离）；同步开发`updateWeights()`逻辑，实现定期的权重更新，形成进化闭环。
   - 网页端开发知识库检索、对局复盘功能。
5. UI优化：
   - 完善牌桌可视化，添加出牌动画、叫牌进程展示、明手摊牌显示。
   - 实现响应式布局，适配电脑、平板屏幕。
   - 开发对局回放功能，支持步进、倒放。
6. 日志与测试：
   - 集成winston日志，记录对局、AI决策、错误信息。
   - 编写单元测试，测试核心规则、AI决策、知识库功能。

**验收标准**：
- 可通过网页端配置规则模板及机器人风格，规则生效且冲突检测正常。
- 支持真人在南位与机器混战，明手摊牌、代理出牌与自动声称功能正常。
- 每局对局结束后数据自动存入知识库，AI可依据特征哈希统计选择最优决策，并具备权重更新能力。
- 对局回放、知识库检索功能正常，UI适配不同屏幕。
- 核心功能无Bug，AI决策响应时间 ≤ 500ms。

### 阶段三：网页版优化与扩展（1周，核心：稳定性+扩展预留+DDS引入）
**核心目标**：优化网页版性能与体验，修复Bug，预留后期APP与联网功能的扩展接口，评估并集成DDS提升AI出牌质量。

**具体任务**：
1. 性能优化：优化AI决策算法（权重表内存化），减少响应时间；优化WebSocket通信，实施增量推送，减少卡顿；尝试集成DDS（Wasm版）作为出牌阶段AI的辅助计算，异步调用不阻塞主线程。
2. Bug修复：修复阶段二发现的规则校验、知识库存储、UI交互等Bug。
3. 扩展接口预留：
   - 后端预留用户体系、匹配撮合、比赛系统、Alert机制的接口。
   - 通用内核依赖的`IKnowledgeRepository`接口已定义，确认APP适配层可无缝实现。
   - 统一通信协议（含序列号、视角掩码与同步模式），确保后期APP与网页端通信兼容。
4. 文档完善：整理核心模块文档、API文档、规则配置说明文档。

**验收标准**：
- 网页版运行稳定，无卡顿、无崩溃，AI决策响应快速，出牌质量经DDS辅助后显著提升。

## 五、开源项目复用与改造细节

### 5.1 核心开源库复用策略

#### 5.1.1 contract-bridge (npm包)
- **复用内容**：牌张模型（Card类）、发牌函数（deal）、牌型分布计算（getDistribution）、定约判定（getContract）、标准计分（calculateScore）。
- **改造内容**：
  - 扩展发牌函数，支持固定牌局复盘（传入指定手牌分布）及局况设定。
  - 扩展计分函数，支持自定义计分规则，考虑局况（对接自定义规则引擎）。
  - 暴露规则校验接口，便于自定义叫牌/出牌规则的集成。
  - 严格进行单元测试，验证其在各种边界条件下的正确性。

#### 5.1.2 devennorton/bridge (GitHub)
- **复用内容**：Node.js+Socket.io通信架构、牌桌UI布局参考、对局状态管理逻辑。
- **改造内容**：
  - 删除原生固定叫牌/出牌规则，替换为自研通用内核与模板化可配置规则引擎。
  - 删除原生简单AI，替换为支持特征哈希匹配、权重进化、风格参数及DDS扩展的智能AI。
  - 改造对局管理逻辑，支持多局连续运行、规则配置切换，并内嵌完整的对局状态机（含明手控制权、声称等）。
  - 优化前端UI，实现响应式布局，添加规则配置面板、机器人风格选择、知识库检索功能。

#### 5.1.3 DDS（Double Dummy Solver，后期引入）
- **复用内容**：第三方的双明手解题器（C/C++源码或预编译库）。
- **集成方式**：编译为WebAssembly供浏览器及Node.js调用，或通过N-API绑定为Node.js原生模块；封装为异步服务（`ddsAnalyze(hand, currentState)`），返回当前局面下每张牌的最优打法及可赢墩数。
- **用途**：AI出牌决策、声称判定、理论与实际差距分析（AI教练）。

### 5.2 改造注意事项
- 保持开源项目的核心逻辑不变，仅做扩展与替换，避免引入不必要的Bug。
- 所有改造均围绕“通用内核+多端适配”架构，确保改造后代码可复用、可扩展。
- 保留开源项目的注释与文档，新增改造部分单独添加注释，便于后期维护。
- 严格遵循开源协议，保留开源项目的版权信息，不侵犯开源权益。

## 六、风险与应对措施

| 风险类型 | 具体风险 | 应对措施 |
|---------|---------|---------|
| 技术风险 | 通用内核抽离不彻底，包含隐式IO调用，导致后期APP离线模式无法正常运行。 | 前期严格按接口倒置原则抽离内核，定义抽象存储接口，每开发一个功能都进行独立测试，确保内核可单独在无Node.js/浏览器依赖下运行。 |
| 技术风险 | 开源项目改造后与自研代码冲突，出现逻辑Bug。 | 改造前彻底熟悉开源项目架构，分模块逐步改造，每改造一个模块进行单元测试，避免一次性大规模改造。 |
| 进度风险 | 自定义规则引擎初期过于复杂，开发难度超出预期。 | 阶段二仅实现模板化配置+冲突检测，将完全自由的参数化配置推迟到后期迭代；利用Claude设计算法逻辑，国产大模型辅助代码生成，提升效率。 |
| 扩展风险 | 后期APP开发与服务器扩展时，与前期网页版架构不兼容。 | 前期严格基于`IKnowledgeRepository`等接口编程，统一通信协议（含同步模式、视角掩码与序列号）；每阶段开发后进行扩展性测试，确保后期扩展无重构。 |
| 性能风险 | 联网模式下，多桌同时对局导致AI查询知识库过慢或服务器压力过大。 | 知识库特征统计采用内存权重表，在线查询避免直接扫描数据库；后期AI出牌采用DDS轻量调用，避免沉重计算；优化代码，后期采用多进程集群+房间分片技术，提升承载能力。 |
| 安全风险 | 服务端视角隔离遗漏，导致暗手数据泄露到客户端。 | 在通信模块强制实现`getMaskedState(seat)`，所有状态推送均经过该掩码；设置自动化测试验证每个座位数据可见范围。 |
| 设计风险 | 规则引擎“通用/完善”目标过度，导致无法收敛。 | 冻结引擎契约（上下文/条件词表/裁决顺序），MVP 只做扁平条件+优先级+兜底；嵌套布尔与打分模型明确推迟；风格用阈值覆盖而非复制规则。 |
| 数据风险 | 随机探索（randomness）污染知识库胜率统计，或不可复现。 | 探索限定在合法且有依据的次优候选之间（ε-greedy）；随机源由 seed 播种；特征统计对“探索偏离”样本单独标注或降权。 |

## 八、总结

本项目采用“通用内核+多端适配”的架构，通过定义抽象存储接口实现核心逻辑与平台的彻底解耦。首期聚焦网页版，支持灵活的真人/机器人混战与机器人风格定制，复用成熟开源资源降低开发成本，同时提前为移动端、联网功能及更高级的AI能力预留扩展接口与协议空间。AI智能方面，通过多级特征哈希加速案例匹配，并引入权重更新闭环与后期双明手求解器（DDS），实现真正可进化的决策系统。桥牌核心机制如明手控制权、声称提前结算、视角安全隔离等均在设计之初深度整合，确保规则严谨、体验流畅。

通过分阶段实施，逐步实现“网页版+APP”、“联网+离线”、“机机对战+人机对战+真人对战”的全场景需求，既保证了首期快速落地，又兼顾了长期扩展性与可维护性。

开发过程中，严格遵循“核心逻辑后端化、接口标准化、UI与业务分离”的原则，利用Claude负责架构设计与复杂逻辑，国产大模型负责代码实现与Bug修复，提升开发效率；同时注重开源资源的合理复用与改造，避免重复造轮子，确保项目高效、高质量落地。
