# 桥牌游戏 MVP 开发文档 V1.4（人机对战，可配置规则引擎）

> 相对 V1.3 的变更：冻结规则引擎接口与条件词表；序列匹配改为“相对座位 token”以支持干扰识别；
> 增加三档机器人风格与 ε 探索（带 seed 可复现）；修正人类控制权模型（`humanSeats`+`controllableSeats`）；
> 修复加倍/再加倍与均型判定等设计缺陷。详见《桥牌游戏mvp-design.txt》。

### 1. MVP 核心目标
开发一个可在浏览器中运行的桥牌游戏，实现：
- 用户坐 **南家**，剩余三家（北、东、西）均为机器人。
- **核心法律硬编码**：叫牌合法性、跟牌义务、赢墩判定、计分等绝对规则用 TypeScript 固化，附带可读说明。
- **策略规则外部化**：叫牌采用声明式 YAML 规则文件，程序启动时加载解析。MVP 内置 **标准精确叫牌法**（裁剪版，覆盖常见序列）。
- **规则引擎边界明确**：叫牌走“数据驱动规则引擎”；打牌以硬编码启发式为主，仅**首攻**由 YAML 规则驱动。信号约定（signals.yml）MVP 仅作文档，不解析。
- **条件匹配**：规则 = 扁平 AND 条件组合（hcp / 控制点 / 花色长度 / 均型…）+ 优先级 + 兜底；条件词表封闭、可扩展。
- **机器人风格与随机性**：每个座位可配 **叫牌风格 / 打牌风格**（0 保守 / 1 正常 / 2 激进），风格以“阈值参数覆盖”实现（非复制规则）；另有 `randomness ∈ [0,1]` 探索度，0 时严格按规则，越大越可能选“次优但有依据”的候选（绝不非法），随机带 seed 可复现。
- **AI 决策**：AI 严格根据规则库匹配叫品并过滤非法动作；人类玩家仅受核心法律约束（可诈叫），不受点力/牌型限制。
- **人类坐庄/明手覆盖**：人类固定坐南。若人类所在方为定约方，人类同时操控庄家与明手两张手牌（涵盖“南做庄、北明手”与“南明手、北做庄”两种情况）；否则仅操控自己。
- **完整对局流程**：发牌（随机+局况）→ 叫牌（Pass/加倍/再加倍）→ 打牌（首攻→明手摊牌→正常打牌）→ 赢墩判定 → 定约结算 → 标准桥牌计分。
- **无高级功能**：不实现自定义规则编辑器、知识库回放、声称/摊牌、多局连续、网络对战、嵌套布尔条件、候选打分模型。

### 2. 技术栈
| 层级 | 技术 | 说明 |
|------|------|------|
| 前端核心 | TypeScript + Vue 3 + Vite + Pinia | 全部逻辑前端实现 |
| UI 组件库 | Element Plus | 辅助布局，牌桌主要自定义组件 |
| 核心引擎 | 自研 | 发牌、法律校验、赢墩判定、计分硬编码 |
| 规则引擎 | 自研 YAML 解析 + 相对座位序列匹配 + 条件判定 + 裁决/探索 | 叫牌体系；首攻规则 |
| 规则文件 | YAML | 可读可编辑；经 Vite `?raw` 构建期内联加载 |
| 规则解析 | js-yaml | YAML → 对象 |
| 测试 | Vitest | 核心法律、引擎、AI 单元测试 |
| 存储 | 无 | 不保存对局记录 |

### 4. 关键业务逻辑设计

- **局况随机**：每局开始时从 `['none', 'NS', 'EW', 'both']` 中等概率随机选取一个作为本局局况，影响最终计分。

#### 4.1 叫牌规则引擎机制（接口已冻结）
- 规则文件为 YAML 格式，每条规则核心包含：
  - `id`：唯一标识
  - `description`：人类可读说明
  - `sequence`：叫牌序列模式。使用**相对座位 token**（`M`=自己 / `P`=同伴 / `L`=LHO / `R`=RHO，相对当前叫牌人），从历史末尾对齐匹配；如 `"P:1C R:Pass"` 表示“同伴刚开叫 1C、RHO 刚 Pass”。特殊值：`^$` = 尚无实质叫品；`.*` = 任意（兜底）。**座位归属显式化，可正确识别敌方干扰**（旧版扁平序列无法区分同伴/对手叫品）。
  - `when`：扁平 AND 条件组合，词表封闭且可扩展：`hcp`、`controls`（A=2 K=1）、`spades/hearts/diamonds/clubs`（长度，如 `"5+"`）、`balanced`（均型：4-3-3-3 / 4-4-3-2 / 5-3-3-2）。区间支持 `"16-40"`、`"0-7"`、`"12"`，并可引用风格变量 `${open1ntMin}` 等。
  - `action`：执行的叫品（如 `1H`、`X`、`XX`、`Pass`）。
  - `priority`：优先级（整数，越大越优先）。
  - `style`（可选）：覆盖部分风格阈值。
- **匹配与裁决机制**：
  1. 引擎筛出**所有**满足“序列匹配 + 座位 + 条件 + **动作合法**”的候选。动作合法性过滤是关键：杜绝 AI 产出低于当前叫品的非法叫品。
  2. 候选按 **优先级↓ → 条件具体度↓（约束项越多越优先）→ 文件声明顺序** 稳定排序（确定性）。
  3. 由 4.7 的裁决/探索算法选出最终动作。
- **兜底规则**：以 `sequence: ".*"`、`priority: 0` 写在文件末尾；按叫牌情景可定义多个不同兜底（如逼叫情境叫最长花色、非逼叫 Pass），避免灾难性停叫。
- **规则无状态**：引擎为纯函数 `(hand, history, currentPos, currentBid, style) => 候选列表`，不保留对局记忆，完全由叫牌历史与手牌推导。
- **契约分离**：叫牌规则与首攻规则是两套独立 Schema（`BiddingRule` / `LeadRule`），共享匹配内核与条件词表；打牌 AI 不走规则引擎。

#### 4.2 人类叫牌自由度
- 人类叫牌面板仅受 `validator.ts` 的层级/加倍等法律约束，**不受规则体系中点力/牌型条件约束**。
- 人类可做心理叫，AI 同伴根据规则匹配不到时会落入对应情境的兜底规则。

#### 4.3 人类控制权模型（冻结）
- 人类固定坐南，`humanSeats = ['S']`。
- 叫牌结束后确定 `contract.declarer` 与 `contract.dummy`。每个行动时点由 `controllableSeats(state)` 计算人类可操作座位：
  - **人类所在方为定约方** → 返回 `[declarer, dummy]`：
    - 南做庄（明手为北）：人类点自己的牌 + 北家明手牌；
    - 南明手（北做庄）：人类点北家（庄家）牌 + 自己摊开的牌。
  - **人类为防守方** → 返回 `['S']`，只操控自己。
- **UI 行为**：
  - 首攻打出后明手牌全摊开。
  - 仅当轮到 `controllableSeats` 内的座位时，对应手牌才可点击（由 `clickable` prop 控制）。
  - 界面显著标识“你处于定约方（庄家/明手）”与“明手已摊牌”。
- **实现说明**：不再使用早期的单字段 `controlledPosition`（它无法区分“南做庄”与“南明手”两种主场景）。

#### 4.4 打牌流程细节（AI 策略边界明确）
- **首攻**：庄家左手方（LHO）打出，首攻前只有南家可见自己手牌。首攻由 YAML 首攻规则（leads.yml）驱动，根据定约类型（有将/无将）匹配约定（如长四、连张首攻、NT 定约攻未叫高级花色）。
- **明手摊牌**：首攻牌打出后，明手牌立刻翻开，全场可见。
- **正常跟牌/打牌 AI**：
  - 实战打牌决策**不**使用 YAML 配置（因逻辑复杂，MVP 范围限定）。
  - 采用硬编码的**基础启发式贪心算法**：
    1. 遵守跟牌法律。
    2. 若本墩当前为最后一家，且手中牌能赢下此墩，出足够赢的最小牌。
    3. 若不能赢，垫当前花色中最小的牌（若无该花色，垫最无价值边花）。
    4. 庄家 AI 做庄时，可利用已摊明的明手牌，优先兑现联手确立赢墩。
  - 若启发式算法选出的牌不合法，则降级为随机选择一张合法牌。
- **AI 延迟**：所有机器人出牌前 `sleep(800ms)`，依次显现。
- **赢墩判定**：硬编码，将牌优先，比较点数大小。

#### 4.5 叫牌结束判定（修正特例）
- **流局**：如果第一轮四家全部 Pass（连续四个 Pass，且无任何叫品），该副牌不打，直接进入 `scoring` 阶段，定约记为 `null`，本局得分 `NS: 0, EW: 0`，UI 弹出“四家不叫，本局流局”提示，并提供新一局按钮。

- **正常结束**：一旦有人做出第一个非 Pass 叫品后，此后出现连续三个 Pass 则叫牌结束，最后一个非 Pass 叫品成为定约。

#### 4.6 计分模块
- 硬编码标准桥牌计分表，根据定约、局况、实际赢墩计算得分。
- 支持有局/无局下的墩分、超墩分、宕墩罚分、成局奖分、满贯奖分、加倍/再加倍。约定：某定约只处于“未加倍 / 加倍 / 再加倍”三态之一（`doubled` 与 `redoubled` 互斥）。

#### 4.7 机器人风格与随机性（新增）
- **风格（0 保守 / 1 正常 / 2 激进）**：每个座位独立配置 `bid`（叫牌风格）与 `play`（打牌风格）。实现方式为**阈值参数覆盖**（`STYLE_PARAMS`），不复制规则文件：
  - 例如 `open1ntMin/open1ntMax`、`overcallMinHcp`、`preemptMinLen`、`inviteMinHcp`、`aggression`。
  - 规则条件中可用 `${open1ntMin}` 等变量引用，从而同一份规则文件在不同风格下表现不同。
- **随机性（ε 探索）**：每个座位配置 `randomness ∈ [0,1]`：
  - `0`：严格按裁决顺序取最优候选（可复现）。
  - `>0`：以该概率在**次优但仍然合法、有依据**的候选中（默认前 2 个）均匀选择，增加不可预测性与趣味性。
  - **硬约束**：探索只在通过合法性过滤的候选间进行，绝不产生非法叫品；无备选时退回最优。
  - 随机源由 `rngSeed` 播种（mulberry32），保证同一局面可复现，便于调试与后续回放。
- 说明：风格负责“稳定性格”，随机负责“小概率探索”，二者相互独立。

### 5. UI 设计要点
- **牌桌方位**：上北、下南、左西、右东。
- **手牌排序**：♠ → ♥ → ♣ → ♦，同花色内 A→2 降序，相邻花色背景色微调。
- **叫牌面板**：按钮 `disabled` 依据 `isCallLegal(history, currentBid, position, call)` 动态计算（含低于当前叫品、加倍/再加倍权限）。
- **视角切换**：`clickable` 由 `controllableSeats(state).includes(position)` 计算；人类为定约方时，庄家与明手两张手牌均可点击，并在明手区域标注“已摊牌”。
- **状态提示**：清晰显示阶段（叫牌中、等待首攻、明手已摊牌、你是庄家/明手等）。
- **风格设置**：开局前可为三个机器人座位分别选择叫牌风格、打牌风格与随机度（0~1）。
- **AI 思考期间禁用交互**：当 `isAiThinking` 为 `true` 时，叫牌面板所有按钮设为 `disabled`，手牌区域添加 `pointer-events: none` 样式并降低透明度，防止玩家在 AI 回合重复点击导致状态机错乱。

### 6. 规则文件 YAML 示例

**叫牌规则片段 (`precision.yml`)**——条件字段为 `when`，序列使用相对座位 token。
```yaml
rules:
  - id: "open_1c"
    description: "精确1C开叫: 16+任何牌型"
    sequence: "^$"                 # 尚无任何实质叫品
    when: { hcp: "16-40" }
    action: "1C"
    priority: 100

  - id: "resp_1d_negative"
    description: "同伴1C、RHO Pass 后示弱1D"
    sequence: "P:1C R:Pass"        # P=同伴, R=RHO
    when: { hcp: "0-7" }
    action: "1D"
    priority: 90

  - id: "overcall_1h"
    description: "RHO 开叫1D 后争叫1H"
    sequence: "R:1D"               # RHO 刚叫 1D，即第二家位置
    when: { hcp: "${overcallMinHcp}-15", hearts: "5+" }
    action: "1H"
    priority: 80

  - id: "fallback_forcing"
    description: "逼叫情境兜底"
    sequence: ".*"                 # 任意未命中序列（写在末尾）
    when: {}
    action: "1S"                   # 叫出最便宜的花色，不Pass
    priority: 0
```

**首攻规则 (`leads.yml`)**——字段为 `when`。
```yaml
rules:
  - id: "nt_4th_best"
    description: "无将定约长四首攻"
    context: { contract_type: "NT" }
    when: {}
    lead: "4th_best_of_longest"
    priority: 10

  - id: "suit_lead_from_honor_sequence"
    description: "有将定约连张首攻"
    context: { contract_type: "suit" }
    when: {}                       # 连张判断在策略实现内完成
    lead: "top_of_sequence"
    priority: 8
```

> `signals.yml`（防守信号）MVP 阶段仅作文档记录，程序不加载解析。

### 8. 测试验收用例

| # | 测试场景 | 预期结果 |
|---|----------|----------|
| 1 | 发牌与排序 | 52 张分发，每人 13 张，UI 按 ♠♥♣♦ 降序排列 |
| 2 | 叫牌面板禁用 | 当前叫品 2♥ 时，低于 2♥ 的叫品按钮被禁用 |

| 11 | 随机性 | `randomness=0` 结果确定；`>0` 时仅从合法候选中偏离；同一 `rngSeed` 可复现 |
| 12 | 首攻规则 | 庄家下家首攻，适用 YAML 约定，延迟 0.8s |
| 13 | 明手摊牌时机 | 首攻打出后明手牌立即全部翻开 |
| 14 | 南家坐庄正常打牌 | 南家庄家时，可点自己手牌和北家明手牌出牌 |
| 15 | 南家明手代打 | 南家明手时，人类控制北家手牌，南家牌摊开且可点击 |
| 16 | 机器人跟牌合法性 | 必须跟领出花色，缺门时才可王杀或垫牌 |
| 17 | 赢墩判定 | 正确判定每墩赢家，13墩后结束 |
| 18 | 计分正确 | 根据定约、局况、墩数、加倍状态计算得分无误 |
| 19 | 规则文件可替换 | 换用备选叫牌规则文件后，AI 行为改变 |
| 20 | 新一局重置 | 完全清理状态，重新发牌、重新播种 |
