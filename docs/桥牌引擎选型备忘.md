## 一、结论先行

可以借鉴，但不建议**整体移植**一个完整引擎。

对本项目最划算的三层策略是：

1. **打牌分析与搜索：接入 DDS（双明手求解器）**
   - 先用它做结果页分析、par 定约、声称校验；
   - 再用“约束采样 + DDS 评估”实现接近单明手的打牌 AI。

2. **叫牌：优先扩展现有 YAML 规则引擎，借鉴成熟项目的约定与推理模型**
   - 不直接换成 BEN/Bridgit 的 2/1 体系；
   - 把它们的约定表、推理方式、竞争叫牌结构翻译成本项目的规则数据。

3. **完整引擎：只作为外部基准或“专家模式”**
   - BEN 很强，但 GPL-3.0，且以固定体系为主；
   - Bridgit 是 MIT，可做叫牌 sidecar；
   - 不建议把 BEN/Bridgit 逐行移植成 TypeScript。

一句话：

> **DDS 补打牌，规则数据补叫牌，完整引擎做基准。**

## 二、当前项目快照

### 2.1 技术架构

- Vue 3 + TypeScript + Vite + Pinia，纯前端，无后端。
- 核心法律硬编码：
  - 叫牌合法性、加倍/再加倍
  - 跟牌义务、赢墩判定
  - 标准复式计分、IMP、贴点制
- AI 与核心法律分离：
  - `src/ai/bidAI.ts`
  - `src/ai/playAI.ts`
- 规则引擎：
  - `src/engine/types.ts`
  - `src/engine/conditions.ts`
  - `src/engine/matcher.ts`
  - `src/engine/arbiter.ts`
- 状态机与 AI 调度：
  - `src/store/game.ts`
- 结果展示：
  - `src/components/DealResultDialog.vue`
  - `src/components/ResultTable.vue`
  - `src/components/ResultPlayTable.vue`

### 2.2 当前能力

- 默认精确叫牌法：`src/rules/bidding/precision.yml`，885 条规则（含斯台曼/转移、2C 应叫、弱二应叫、开叫人再叫、竞争叫牌等）。
- 备选自然叫牌法：`src/rules/bidding/natural.yml`，约 23 条规则。
- 首攻规则：`src/rules/play/leads.yml`，4 条规则。
- 跟牌/垫牌：`src/ai/playAI.ts` 启发式；设置开启时优先使用 `src/ai/dds/play.ts` 的隐藏牌抽样 + DDS 评估，失败自动回退。
- 已有防守信号约定，但主要是文档 + 启发式实现。
- `src/benchmark/` + `scripts/benchmark.ts` 提供固定种子、Par 对照和 DDS vs 启发式的对抗基准。

### 2.3 当前限制

叫牌条件词表已扩展，`ConditionSpec` 目前包括：

- `hcp`
- `controls`
- `spades / hearts / diamonds / clubs`
- `balanced`
- `losers`
- `voids / singletons / doubletons`
- `fourCardMajor / fiveCardMajor`
- `aces / kings`
- `stoppers`（如 `"SHD"`）
- `openingSeat`
- `partnerOpened`（区分应叫开叫与应叫争叫/再叫）
- `partnerHcp`（同伴 HCP 下限的保守推断）
- `combinedHcp`（自己 HCP + 同伴 HCP 下限）

`partnerHcp` / `combinedHcp` 的推断位于 `src/engine/partnerInference.ts`，只在同伴为
本副第一个实质叫牌人时启用，覆盖精确 1C、1NT、一阶花色、2NT、2C/2D、弱二与阻击等
明确开叫；1C-1NT 后 2H 按 16+ 的自然再叫处理，2S 按 19+ 的强再叫处理（只认无争叫
形态，竞争叫牌或 1D 负应后的再叫仍按 16+ 保守处理）；1C-1NT-3NT 是 16-18 均型且
无四张高花的封局，只按 16+ 推断。推断无法确定时条件不成立，避免误命中。

仍未支持：花色质量、关键张、局况/加倍状态、对手已显示点力/牌型的推理、配合长度等。

仍缺少：

- 搭档牌型推理；点力目前只有“同伴开叫人”的保守下限
- 对手叫牌含义与约定卡提醒
- 花色质量、关键张、总点
- 局况/IMP/MP 对叫牌策略的动态影响
- “这个叫品向搭档承诺了什么”的双向语义
- 更精细的竞争叫牌与逼叫进程

打牌方面已具备隐藏牌抽样、DDS 批量评估与启发式回退；仍缺少：

- 单明手搜索/更精细的分布推断
- 防守信号与庄家读牌的显式推理
- 声称/摊牌校验

## 三、开源项目调研

### 3.1 候选清单

| 项目 | 许可证 | 能力 | 形态 | 建议 |
|---|---|---|---|---|
| **DDS / DDS3** | Apache-2.0 | 双明手求解、par、逐张分析 | C++，可编译 WASM | ★首选，接入打牌分析 |
| **bridge-dds-js** | Apache-2.0 | DDS 的 JS/WASM 封装 | TypeScript + WASM | 浏览器接入最快 |
| **endplay** | MIT | Python 桥牌工具，封装 DDS | Python | 适合离线分析/脚本，不适合浏览器 |
| **BEN** | GPL-3.0 | 叫牌 + 打牌 + 分析，接近 WBridge5 水平 | Python/TF + REST API | 只做外部基准/专家模式 |
| **Bridgit** | MIT | 仅叫牌，2/1 LC Standard | C#/.NET Standard 2.0 | 可做 sidecar，或借鉴规则表 |
| **pons** | MIT/Apache-2.0 | 2/1 GF 叫牌、推理、DD 搜索 | Rust | 借鉴规则与推理架构，可考虑 WASM |
| **BRL** | Apache-2.0 | 仅叫牌，论文 +1.24 IMPs/board vs WBridge5 | Python/JAX | 研究基准，不适合直接产品化 |
| **rusty-bidding-bot** | MIT/Apache-2.0 | 规则叫牌，带解释，WASM | Rust | 架构很对口，但仍是 early design |
| **BBA/EPBot** | 免费非商业，非开源 | 很强，成熟基准 | C/C++ | 只能做基准，不能移植 |
| **WBridge5** | 免费闭源 | 很强 | Windows | 只能做基准，不能移植 |
| **LibreBridge** | GPL-3.0 | 随机 AI，功能简单 | C++/Qt | 不适合作为引擎来源 |
| **kduffie/bridge-engine** | MIT | TypeScript 桥牌框架，机器人是占位实现 | TypeScript | 可参考 API 设计，不是强引擎 |

### 3.2 关键事实

- 真正“成熟且完整”的开源引擎很少。
  - 最强的 WBridge5、BBA/EPBot、GIB、Jack 都不是开源。
- **BEN** 是开源里最完整的之一：
  - GPL-3.0；
  - Python 3.12 + TensorFlow 2.18 + DDS3；
  - 提供 REST API（默认端口 8085），端点包括 `/bid`、`/lead`、`/play`、`/claim`、`/explain`；
  - 以 2/1/SAYC 为主，不能像本项目这样用 YAML 自由配置精确体系；
  - 对手提醒/约定卡支持有限。
- **Bridgit**：
  - MIT；
  - C#/.NET Standard 2.0，约 85 个 C# 源文件；
  - 仅叫牌，2/1 LC Standard；
  - 输入输出可用 PBN 字符串，适合包一层 REST；
  - 逐行移植到 TypeScript 成本较高。
- **pons**：
  - MIT/Apache-2.0；
  - Rust，2/1 GF 叫牌体系、推理引擎、学习型 floor、DD 搜索；
  - 仅有叫牌，不含完整打牌 AI；
  - 目前未做 WASM 适配，但架构值得借鉴；
  - 其 `docs/archive/open-source-bidder-survey.md` 是一份很有价值的开源叫牌引擎调研。
- **BRL**：
  - Apache-2.0；
  - 论文报告 +1.24 IMPs/board vs WBridge5；
  - 但只测叫牌、用 DDS 计分，不是完整打牌；
  - 研究代码，无现成服务 API，不适合直接产品化。
- **rusty-bidding-bot**：
  - MIT/Apache-2.0；
  - Rust + WASM，规则数据驱动，支持约定卡和叫牌解释；
  - 架构和本项目非常契合；
  - 但仍是 early design，暂不宜作为生产依赖。
- **DDS**：
  - Apache-2.0；
  - 双明手求解，不是单明手 AI；
  - 直接让 DDS 拿四家牌出牌等于作弊；
  - 正确用法是作为评估器/搜索内核，配合隐藏牌采样。
- **BBA/EPBot、WBridge5**：
  - 免费但闭源；
  - 只能作为基准或对手，不能反编译/移植。

### 3.3 强度参考

来自 pons 的 2026-07 调研（注意：多为叫牌-only、DD 计分、跨测试框架，不能直接等同于完整对局强度）：

```text
WBridge5（闭源，多次世界冠军）
  +0.25  Rong 2019
  +0.41  Gong 2019
  +0.63  Tian/JPS 2020
  +0.85  Lockhart 2020
  +0.98  Qiu 2024
  +1.24  Kita/brl 2024（开源，代码 + 权重）
  ≈0     BEN v0.2 2024（非正式比赛）
```

BBA 自家测试中：

- BEN v0.8.8.4 对 EPBot 约 +0.35 ~ +0.38 IMPs/board（DD）；
- EPBot 对 WBridge5 约 -0.40 IMPs/board（DD）；
- 因此 BEN 大致接近 WBridge5 水平；
- pons 约比 EPBot 低 1.7 ~ 1.9 IMPs/board。

这些数字只能作为选型参考，不能直接用来承诺产品强度。

## 四、推荐路线

### 第 0 步：先建基准，再谈“更强”

目标：能客观判断某个改动是否真的变强。

建议做：

- PBN 导入/导出；
- 固定种子、重复牌局；
- IMP/MP 双计分；
- 指标：
  - 每副 IMP
  - 定约分布
  - 与 DD par 的差距
  - 每次决策耗时
- 当前 AI vs 外部引擎的对照。

可复用：

- `src/core/scoring.ts`
- `src/core/imps.ts`
- `src/store/game.ts`
- `src/testing/testUtils.ts`

### 第 1 步：接 DDS，先做“分析”而不是“AI”

这是风险最低、收益最直接的一步。

建议：

- 用 `bridge-dds-js` 或 DDS3 的 Emscripten 构建；
- 放在 Web Worker 中，避免阻塞 UI；
- 在 `DealResultDialog.vue` / `ResultTable.vue` 增加：
  - 20 个定约的双明手结果表
  - 最佳定约 / par contract
  - 每张已出牌的 DD 价值
  - 声称（claim）校验
- 不改变现有 `playAI` 行为。

预期：几天到一周，先让产品具备“复盘/分析”能力。

### 第 2 步：DDS + 约束采样升级打牌 AI

核心思路：

1. 根据叫牌过程、已出牌、明手牌，采样 N 个符合约束的隐藏牌分布；
2. 对每个合法出牌，用 DDS 求解，计算期望墩数/期望得分；
3. 选期望值最高的牌；
4. 失败时回退到现有 `playAI`。

落地建议：

- 新建 `src/ai/play/monteCarlo.ts`；
- 新建 `src/ai/dds/` 适配层；
- 先做首攻和庄家打法，再做防守；
- 放在 Worker 中，限制样本数并缓存；
- 用现有 392 个测试作为回归基线。

注意：

- 这是“单明手近似”，不是完美解；
- DDS 假设四家明牌、完美防守，直接拿完整四手牌出牌等于作弊；
- 实战路径必须只使用自己手牌、明手、已出牌和剩余张数，采样合法隐藏分布后再交给 DDS；
- “采样 + DD 评估”是 BEN、pons 一类引擎的常见做法，当前实现相对纯启发式约 +6 IMP/副。

### 第 3 步：叫牌升级，优先扩展现有 YAML

这是保持产品差异点的关键。

建议扩展 `src/engine/types.ts` / `src/engine/conditions.ts`：

- 形状模式；
- 花色质量；
- 止张；
- 输墩；
- 总点；
- 关键张；
- 局况、计分方式；
- 是否被加倍；
- 搭档/对手已显示的点力与牌型；
- 配合长度；
- 竞争叫牌上下文。

同时给规则增加 `shows` 语义：

- 自己叫牌时检查手牌是否满足；
- 搭档叫牌时记录“搭档承诺了什么”；
- 后续规则可以引用 `partner.hcp`、`partner.suits`。

规则来源：

- 从 Bridgit 的 LC Standard 约定表翻译；
- 从 pons 的 2/1 规则、推理模型、竞争叫牌结构借鉴；
- 从 rusty-bidding-bot 的约定卡/解释模型借鉴；
- 保持 YAML/JSON 数据驱动，不把规则写死在代码里。

如果确实需要 2/1 模式：

- 用 **Bridgit（MIT）** 做 .NET sidecar；
- 前端通过 `/bid` 调用；
- 保留现有精确体系作为默认/离线模式。

### 第 4 步：BEN 只作为“外部基准/专家模式”

不建议直接嵌入产品：

- GPL-3.0，商业分发需要认真评估；
- Python + TensorFlow + DDS，运行时重；
- 固定体系为主，和可配置精确体系不一致。

适合：

- 生成基准对局；
- 作为“专家分析”后端；
- 蒸馏叫牌策略；
- 评估自己规则覆盖度。

### 第 5 步：可选实验

- 跟踪 `rusty-bidding-bot`，等它成熟后评估 WASM 接入；
- 评估 pons 编译到 WASM 的可行性；
- 评估 `bridge-dds-js` 在移动端的性能；
- 如果需要服务端，考虑 DDS/BEN/Bridgit 的 sidecar 部署。

## 五、不建议的做法

1. **不要把 BEN 或 Bridgit 整体移植成 TypeScript**
   - 成本高；
   - 许可证和体系不匹配；
   - 会重复已有状态机、计分和 UI。

2. **不要让 DDS 直接决定出牌**
   - 双明手信息不合法；
   - 必须配合隐藏牌采样。

3. **不要混用叫牌体系**
   - BEN/Bridgit 打 2/1/SAYC；
   - 本项目默认精确；
   - 混用会产生无法解释的叫牌序列。

4. **不要忽略许可证**
   - DDS / Bridgit / pons / BRL：Apache/MIT，适合产品；
   - BEN：GPL-3.0；
   - BBA/WBridge5：免费但闭源，只能做基准。

5. **不要在没有基准的情况下换引擎**
   - “看起来更强”不等于“实际更强”；
   - 先做 PBN + 固定种子 + IMP/MP 回归。

>   当前精确制规则 100 副为平均 **+1.49 IMP/副（NS 视角）**、绝对偏差 **2.53 IMP/副**，
>   漏局 9、漏贯 3、超叫 2、流局 0；规则总数 **896** 条。
>   扩大到 1000 副（seed=2026）时为 **+0.42 IMP/副**、绝对偏差 5.17，漏局 287、漏贯 97、超叫 46、流局 3，
>   说明小样本参考值偏乐观，后续应优先用绝对偏差和漏局/漏贯定位系统性缺口。
> - 1C-1NT-2S 的 2S 现在明确为 **19+ 且 5+ 黑桃**（2H 仍是 16+ 的自然再叫）；
>   应叫人 10 点、4+ 黑桃、
>   2+ 控制且联手 29+ 时用 4NT 问 A，后续按 0/4→5C、1→5D、2→5H、3→5S
>   答叫，并在 5H/5S 后补到 6S；5C-5S 后开叫人持 4 A 再改叫 6S。
> - 新增 `partnerHcp` / `combinedHcp` 条件与保守的同伴点力下限推断，用于满贯门槛；
>   目前只覆盖“同伴是开叫人”的明确序列。
> - 修正 `1C-1NT-3NT`：由误写的 22+ 改为 **16-18 均型且无四张高花的封局**；
>   19+ 未命中自然再叫时改用 2NT 兜底，避免 3NT 承载多种点力区间。
> - 新增叫牌含义浮窗、人类推荐叫品自动选中/高亮、推荐出牌箭头与理由浮层，以及设置中的
>   “显示提示与推荐”总开关；含义优先读取 `BidRecord.ruleId`，人类改选时实时预览。
> - `signals.yml` 升级为可浏览的打牌细则文件（settings + rules + conventions），
>   规则管理新增第三页签；`signal_spot_max_rank` 与 `encourage_discard_min_rank`
>   由 `playAI` 直接读取，修改后可立即验证跟牌/垫牌行为。
> - `M:` 开头规则现在要求自己完成本副第一次实质叫牌，避免把再叫误当开叫；
>   同时修正了 `1S-2D-3C` 后应叫人再叫的座位 token。
>
> 下一步方向：
> 1. 满贯探索：补 1C-1NT-2S 后的关键张/将牌 Q 问叫，并评估 2NT 开叫后的满贯进程。
> 2. 1C-1NT 后 16-18 点、4+ 高花的探索叫品与应叫人续叫，避免这类牌只能落到 2NT。
> 3. 防守信号：从同伴/对手的跟牌、垫牌中解析张数/态度，作为隐藏牌抽样的后验。
> 4. 叫牌模拟：对关键成局/满贯决策用双明手表评估候选定约，逐步替代纯规则优先级。
> 5. 首攻推断：用 `leads.yml` 的首攻约定反推首攻人牌型，而不仅是“低引=长套”。
> 6. 规则评估：继续用 `bidding-eval` 的绝对偏差与漏局/漏贯定位系统性缺口，避免只修单副牌。
> 7. 复核 `1C-1H/1S/2C/2D` 后的 3NT：目前仍写成 22+ 封局，应按 19-21 均型封局
>    或 4NT 定量满贯试探重新分层，避免 22+ 反而错过满贯。

### 6.5 待确认问题

下次开始前需要先确认：

1. 产品定位：
   - 继续保持“可配置精确叫牌法”？
   - 还是优先追求“最强 AI”，可以切换到 2/1？
2. 部署形态：
   - 纯前端/离线优先？
   - 还是可以接受 .NET/Python sidecar？
3. 许可证：
   - 项目是否允许 GPL 依赖？
   - 是否商业分发？
4. 性能：
   - DDS WASM 在目标设备上的可接受延迟是多少？
   - 是否需要服务端求解？
